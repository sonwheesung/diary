## 1. 조각이란

하루에 대한 기록 하나. 구성은 **제목(선택) · 본문(필수) · 이미지(선택) · 태그(선택) · 감정(선택) · 날짜**다.

- ~~제목은 선택~~ → ~~정정(2026-08-08): 제목은 필수다~~
  → **되돌림(2026-08-19, 사용자 결정): 제목은 다시 선택이다.**
  필수화의 근거는 *"목록·검색·캘린더에서 알아보는 단서"* 였는데, 그건 **읽는 쪽 편의**이고
  대가는 **쓰는 쪽 마찰**이다 — 기둥 1이 이긴다. 한 줄 쓰고 닫으려는 사람에게
  제목 칸을 하나 더 요구하면 그 조각은 안 남는다.
  단서가 없어지는 것도 아니다: 목록은 **날짜·감정·본문 앞부분**을 이미 갖고 있다.
- 빈 본문은 저장하지 않는다(공백만 있는 것도 빈 것으로 본다).
  단, **이미지만 있고 글이 없는 조각은 허용한다** — 사진 한 장이 그날의 기록일 수 있다.
- 감정·태그·이미지는 여전히 **선택**이다. 여기까지 요구하면 기둥 1(쓰기 마찰 최소화)에 어긋난다.
- 저장을 막는 것은 **본문뿐**이다. 빈 제목은 `normalizeTitle`이 `null`로 바꿔 저장한다 —
  `''`로 두면 목록이 빈 줄을 그린다.
- ⚠ **되돌리기가 싼 방향으로 설계돼 있었다.** `title` 컬럼은 필수이던 동안에도 NULL을 허용했고
  (제목 없이 저장된 옛 조각·다른 기기에서 복원된 조각을 읽어야 해서), 목록·검색·상세는 전부
  `title !== null`로 가려 그린다. 그래서 이 되돌림은 **UI 게이트 한 줄**을 지우는 일이었다.
  데이터 계층에 강제를 박았다면 마이그레이션이 필요했을 것이다.

> **작성 화면 구조(2026-08-07 확정)**: 제목 입력 → 본문 입력(본문 **중간 원하는 위치에 이미지 삽입**)
> → 본문 아래 태그 추가. 디자인 시안의 작성 화면은 **톤·색감 참고용**이며 구조는 위를 따른다.
> 시안에 있던 위치·음악 첨부, 그리기 도구는 도입하지 않는다.

> **작성 화면 레이아웃(2026-08-08 결정)**: **페이지를 스크롤하지 않는다.**
>
> | 영역 | 위치 |
> |---|---|
> | 헤더 | 닫기(X) · 저장 버튼 |
> | 날짜 | 큰 일(日) 숫자 + 월·연·요일. 누르면 날짜 시트 |
> | 기분 | 날짜 오른쪽 원형 버튼. 고르면 라벨이 그 자리에 들어온다 |
> | 제목 | 선택 입력 |
> | 본문 | **남는 공간 전부.** 이 영역만 스크롤한다 |
> | 태그 | 고른 태그만 칩으로 본문 아래 한 줄 |
> | 툴바 | 바닥 고정 — 사진 · 태그 · 기분 |
>
> 왜: 페이지가 스크롤되면 글을 쓸 때마다 아래 요소가 밀리고, 감정·태그를 고르려면 매번 스크롤해야 한다.
> 가끔 쓰는 선택은 하단 툴바에서 **시트로 열고 닫는다**(`components/BottomSheet`).
> 각 텍스트 칸은 영역 높이를 넘지 못하게 잡아, 그 지점부터는 입력창이 자기 안에서 스크롤한다 —
> 바깥 스크롤뷰는 타이핑 중 커서를 따라오지 못한다.

## 1.1 본문 모델 — 블록 배열 (2026-08-07 결정)

본문은 평문이 아니다. **텍스트 · 목록 · 이미지 블록의 순서 있는 배열**이다.

```jsonc
[
  { "type": "text",  "value": "오늘은 하늘이 정말 예뻤다." },
  { "type": "image", "imageId": "9f3c…" },
  { "type": "text",  "value": "커피를 마시며 한참 봤다." }
]
```

**왜 블록인가 (마크다운·HTML이 아니라)**

- RN에서 인라인 리치 텍스트 편집(한 TextInput 안에 이미지가 끼어드는 형태)은 네이티브 제약이 크다.
  WebView 에디터를 얹으면 오프라인·잠금 중심 앱에 과한 무게와 보안 표면이 생긴다.
- 블록 단위면 **순수 RN 컴포넌트**(문단마다 TextInput, 사이에 이미지 뷰)로 구현된다.
- AI 요약에 넘길 때 **텍스트 블록만 뽑으면 된다** — 마크업 파싱이 필요 없다.
- 백업 암호화도 블록 단위로 다루기 쉽다.

### 목록 블록 (2026-08-09 추가)

```ts
{ type: 'list', items: string[] }
```

**불릿 모양은 저장하지 않는다.** 모양은 표시 문제라 나중에 스킨(CLAUDE.md §9)에서 갈아끼울 수
있어야 하고, 저장해두면 스킨을 바꿔도 옛 조각만 옛 모양으로 남는다 — 감정을 라벨이 아니라
코드로 저장한 것과 같은 이유다.

- 사진과 **같은 규칙**으로 커서 자리에 끼운다(§1.2).
- 엔터로 다음 항목을 만들고, **빈 항목에서 엔터를 치면 목록을 끝낸다** —
  목록을 빠져나오는 유일하게 자연스러운 손동작이다.
- 마지막 항목을 지우면 **목록 블록 자체가 사라진다.** 빈 목록이 남으면 지저분하다.
- 빈 항목은 저장 시 `normalizeBlocks`가 버리고, 전부 비었으면 블록째 버린다.
- ⚠ **평문 파생에 목록 항목을 반드시 포함한다.** 빠뜨리면 "감사한 것 3가지"를 목록으로 적은
  조각이 검색에서 통째로 사라진다 — 분명히 썼는데 안 찾아지는 게 가장 나쁘다.

**검색용 평문은 따로 저장한다.** 블록 JSON을 그대로 `LIKE`로 긁으면 `"type"`, `"image"` 같은
구조 문자열이 검색에 걸린다. 그래서 텍스트 블록만 이어붙인 평문을 별도 컬럼에 **파생 저장**한다.

- 정본은 블록 배열이다. 평문은 **항상 블록에서 재생성**되는 파생 데이터다.
- 저장 시 두 값을 같은 트랜잭션에서 함께 쓴다 — 어긋나면 검색이 조용히 틀린다.

### 🔴 빈 텍스트 블록이 남으면 **지울 길이 없었다** (2026-08-27 · 실기기 v13에서 신고)

사용자 신고: *"목록을 만들고 지우고 하다가 빈 줄이 4줄쯤 됐는데 삭제가 안 된다."*
실기기(SM-S921N · vc13) 접근성 트리 실측 — 본문 뒤에 **`len=0`인 텍스트 블록 두 개**가
쌓여 있고 커서가 마지막 것에 있었다.

```
#8  EditText len=4   제목
#9  EditText len=20  본문
#10 EditText len=0   ← 빈 블록
#11 EditText len=0   ← 빈 블록 (커서)
```

#### 어떻게 만들어지나

```
insertList()        텍스트를 [앞, 목록, 뒤] 로 쪼갠다.
                    커서가 문단 끝이면 '뒤'는 **빈 텍스트 블록**이다 — 이건 의도된 것이다.
                    목록 다음에 이어 쓸 자리가 없으면 글이 목록에서 끊긴다.
목록 항목 전부 삭제  removeListItem 이 목록 블록만 splice 로 걷어낸다.
남는 것             [본문, 빈 텍스트]  ← 두 번 반복하면 빈 블록이 둘
```

**만든 쪽은 잘못이 없다.** 잘못은 **걷어낸 쪽이 뒷정리를 안 한 것**이다 —
사이에 있던 블록이 빠졌으면 앞뒤 텍스트 블록은 다시 한 문단이어야 한다.

#### 왜 지울 수 없었나 — 세 가지가 겹쳤다

| | |
|---|---|
| `onKeyPress` 처리가 **0건** | `BlockEditor`·`DiaryEditor`·`components/TextField` 어디에도 없다. 빈 칸에서 백스페이스를 눌러도 `onChangeText`는 안 불린다 — **지울 글자가 없기 때문**이다. 그래서 아무 일도 안 일어난다 |
| 삭제 버튼은 **사진에만** 있다 | `removeBlock()`은 존재하는데 호출부가 이미지 블록 하나뿐이다. 텍스트 블록에는 없앨 손동작이 없다 |
| 정리는 **저장할 때만** 돈다 | `normalizeBlocks`가 빈 텍스트 블록을 버리지만 그건 저장 직전이다. 편집 중 화면에는 그대로 남는다 |

🔴 **셋 중 마지막이 이 버그의 성격을 정한다.** 데이터는 멀쩡하다 — 저장하면 빈 줄은 사라진다.
망가진 것은 **편집 중 화면과 저장 결과가 갈린다**는 것이고, 사용자에게는 그 구분이 안 보인다.
*"저장하면 없어져요"* 는 설명이지 해결이 아니다.

#### 형제 경로 — 목록만의 문제가 아니다 (전수)

블록을 쪼개거나 걷어내는 자리를 전부 세어 봤다:

| 자리 | 빈 블록을 남기나 |
|---|---|
| `DiaryEditor.insertList` | 뒤 조각. **의도됨**(이어 쓸 자리) |
| `DiaryEditor.insertImage` | 뒤 조각. **의도됨** — 같은 규칙 |
| `BlockEditor.removeListItem` (마지막 항목) | 🔴 목록을 걷어내며 **앞뒤 텍스트를 안 합친다** |
| `BlockEditor.removeBlock` (사진 삭제) | 🔴 같은 문제. 사진을 지우면 앞뒤 문단이 인접한 채 남는다 |
| `format.splitParagraph` | ✅ **안 남긴다** — `if (before.length > 0)` 가드가 있다 |

🔴 **옳은 패턴이 이미 같은 코드베이스 안에 있었다.** `splitParagraph`는 빈 조각을 안 만드는데
삽입·제거 두 쌍은 그걸 안 따랐다. 새로 발명할 것이 없었다는 뜻이고,
**"이 코드베이스가 이미 하는 방식"을 안 찾아본 것**이 진짜 원인이다.

#### 왜 검사가 못 잡았나

이 건을 고치기 전에도 `npm run check:diary-format` 28개가 **전부 통과**했다. 당연하다 —
그 검사는 **순수 계층**(`blocks.ts`·`format.ts`)을 보고, 거기서는 `normalizeBlocks`가
빈 블록을 정확히 버린다. **저장 결과는 처음부터 옳았다.**

틀린 것은 **화면이 저장 전까지 보여주는 중간 상태**이고, 그건 RN 컴포넌트 상호작용이라
순수 함수로 잴 수 없다. 2026-08-24 커서 버그와 **정확히 같은 종류**다
(*"순수 계층 검사로는 원리적으로 못 잡는다"* — §1.1 커서 잠금).

⏭ 그래서 이 둘은 가드가 아니라 **실기기·에뮬레이터 확인 항목**으로 관리한다.

### 🔴 규약 — 블록 에디터를 만들 때 조심할 것

> 체크리스트·메모·노트처럼 **블록 배열을 편집하는 앱**을 또 만들면 이 절을 먼저 읽는다.
> 아래 넷은 조각에서 실제로 물린 것이고, 넷 다 *"기능은 되는데 되돌릴 수가 없다"* 는 한 가지 모양이다.

1. **넣는 손동작을 만들면 빼는 손동작도 같이 만든다.**
   삽입은 버튼이 있어서 눈에 띄고, 제거는 키보드 뒤에 숨어 있어서 잊는다.
   조각은 사진에만 삭제 버튼이 있었고 빈 문단에는 아무것도 없었다.

2. 🔴 **블록을 걷어낼 때 이웃을 다시 붙인다.**
   가운데 것이 빠졌으면 앞뒤는 한 덩어리로 돌아가야 한다.
   안 붙이면 **눈에 안 보이는 경계**가 남고, 사용자는 "빈 줄"로만 인식한다.

3. 🔴 **"저장할 때 정리한다"는 편집 중인 사람에게 아무 도움이 안 된다.**
   정규화가 저장 시점에만 돌면 **화면과 데이터가 갈린다.**
   사용자는 화면을 보고 판단하므로, 화면이 틀리면 그냥 버그다.
   → 정규화 규칙 중 **사용자가 되돌릴 수 없는 상태를 만드는 것**은 편집 중에도 적용한다.

4. 🔴 **빈 칸에서는 백스페이스를 받을 방법이 없다** — 안드로이드에서 실측했다.
   `onChangeText`는 지울 글자가 없어 안 불리고, **`onKeyPress`도 Backspace를 주지 않는다.**

   | 실측(2026-08-27 · 에뮬레이터 `diary` · RN 0.81 Fabric) | |
   |---|---|
   | 배치 | `[AAAA][빈 문단]` — 앞이 텍스트라 병합 조건을 만족 |
   | 동작 | `onKeyPress`에 병합을 붙이고 `KEYCODE_DEL` 입력 |
   | 결과 | **빈 문단이 그대로 남았다.** 핸들러가 아예 안 불린다 |

   → 붙였던 `onKeyPress` 병합은 **되돌렸다.** 동작하지 않는 코드를 남기면
   다음 사람이 *"백스페이스 병합은 이미 있다"* 로 읽고 진짜 원인을 다시 안 찾는다.

   **그래서 이 앱은 빈 문단을 만들지 않는 쪽으로 막는다**(규약 2) — 빠져나오는 손동작이 아니라
   **애초에 안 생기게** 하는 것이 유일하게 작동하는 방어다.

   ⏭ 그래도 하나 남는다: **서식을 걸어 문단을 쪼갠 뒤 그 문단의 글자를 다 지우면**
   빈 문단이 남고 편집 중에는 못 지운다(저장하면 `normalizeBlocks`가 버린다 — 데이터는 멀쩡하다).
   🚫 *"비면 자동으로 앞 문단과 합친다"* 로 막지 **않았다** — H1을 걸어놓고 글자만 지운 뒤
   다시 쓰려는 사람의 **서식 의도까지 지워버린다.** 눈에 보이는 삭제 버튼을 다는 쪽이 맞지만,
   빈 문단마다 버튼이 뜨는 그림이 기둥 2(조용한 화면)와 부딪혀 **보류한다.**

⚠ 그리고 이 넷은 **순수 계층 검사를 전부 통과한 채로** 일어난다.
저장 결과만 검사하면 영원히 안 보인다 — **편집 중 상태를 눈으로 보는 절차**가 따로 있어야 한다.

### 텍스트 서식 (2026-08-24 추가 · 사용자 결정)

텍스트 블록은 **정렬 · 크기 · 굵기 · 글자색**을 가질 수 있다. 전부 **선택**이고, 없으면 기본값이다.

```jsonc
{ "type": "text", "value": "오늘은 하늘이 정말 예뻤다.",
  "align": "center",   // left(기본) | center | right
  "size":  "h2",       // h1 | h2 | h3 | h4 | body(기본)
  "bold":  true,       // 기본 false
  "color": "rose" }    // ← 코드다. hex가 아니다
```

#### 🔴 색은 **코드**로 저장한다 — hex를 저장하지 않는다

감정을 라벨이 아니라 코드로 저장한 것과 **같은 이유**다(CLAUDE.md §9.1 규칙 2).
`theme/palettes.ts`가 라이트·다크 각각의 실제 색을 갖고, 블록은 `rose` 같은 이름만 든다.

hex를 저장하면 **라이트에서 고른 진한 자주색이 다크모드에서 안 읽힌다.** 참고한 일기장들의
색 팔레트는 전부 밝은 배경 전용이라 그대로 가져오면 그 사고가 그대로 온다.
스킨(CLAUDE.md §9)이 붙어도 마찬가지다 — 코드로 두면 팔레트가 갈아끼워지고,
hex로 두면 **옛 조각만 옛 색으로 남는다.**

#### 목록 블록의 *"모양은 저장하지 않는다"* 와 어긋나지 않는가

어긋나지 않는다. 둘의 차이는 **누가 골랐는가**다.

| | 불릿 모양 | 텍스트 서식 |
|---|---|---|
| 누가 정했나 | **아무도 안 골랐다** — 렌더러 기본값 | **글쓴이가 골랐다** |
| 스킨이 바꿔도 되나 | 된다. 그게 스킨의 일이다 | 🚫 안 된다. 글쓴이의 의도다 |
| 저장 형태 | 저장 안 함 | **코드**(값이 아니라 이름) |

즉 저장하는 것은 *"이 문단은 장미색이다"* 가 아니라 *"이 문단은 `rose` 역할이다"* 이고,
그 역할이 어떤 픽셀이 되는지는 **여전히 테마가 정한다.** 불릿 결정이 막으려던 것
(*"스킨을 바꿔도 옛 조각만 옛 모양으로 남는 것"*)은 그대로 막힌다.

#### 서식을 적용하면 그 문단이 **자기 블록으로 떨어진다**

이건 취향이 아니라 **강제**다. 텍스트 블록 하나는 `TextInput` 하나이고,
**RN의 `TextInput`은 한 입력창 안에서 문단마다 다른 크기를 그리지 못한다.**
그래서 "3번째 문단만 H1"을 편집 중에 보여줄 방법이 블록 분할 말고는 없다.

```
적용 전   [text: "가\n나\n다"]                     ← 커서가 "나"에 있음
적용 후   [text: "가"] [text: "나", size:h1] [text: "다"]
```

- 분할은 **서식을 적용하는 순간에만** 일어난다. 그냥 엔터를 치는 것은 지금처럼 한 블록 안이다 —
  항상 문단마다 블록을 만들면 백스페이스 병합·커서 점프를 전부 다시 짜야 하고,
  그건 RN 편집기가 가장 잘 깨지는 자리다.
- 서식을 **기본값으로 되돌리면** 이웃과 다시 합쳐진다(아래 `normalizeBlocks`).

#### `normalizeBlocks`는 **서식이 같을 때만** 합친다

지금은 연속된 텍스트 블록을 `\n`으로 무조건 합친다. 그대로 두면 **저장하는 순간 서식이
전부 사라진다** — 서식이 다른 두 블록이 하나로 뭉개지기 때문이다.

- 합치는 조건에 *"서식이 같다"* 를 더한다.
- 서식이 **전부 기본값이면 필드를 아예 쓰지 않는다.** 그래야 서식을 한 번도 안 건드린 조각의
  JSON이 **오늘과 바이트 단위로 같다** — 옛 조각이 이유 없이 커지거나 백업 diff가 튀지 않는다.

#### 검색·AI·백업은 영향이 없다

- **검색**: `plainText`는 `value`만 이어붙인다. 서식은 파생에 들어가지 않는다.
- **AI 리포트**: 텍스트 블록의 글자만 뽑아 보낸다 — 마크업이 프롬프트에 새지 않는다.
- **백업**: `content_blocks`는 JSON 문자열째로 실린다. **DDL 변경이 없어 마이그레이션도 없다.**

⚠ **옛 앱으로 복원하면 서식이 지워진다.** `parseBlocks`는 모르는 필드를 들고 있지만
`normalizeBlocks`가 블록을 다시 만들면서 버린다. 즉 서식이 들어간 백업을 v9 이하 빌드에서
복원하고 **거기서 수정하면** 그 조각의 서식이 사라진다. 읽기만 하면 무해하다.
이건 감수한다 — 막으려면 `MANIFEST_FORMAT`을 올려 옛 앱의 복원 자체를 거절해야 하는데,
**서식 하나 때문에 복원을 막는 것이 훨씬 나쁘다.**

#### 🔴 커서 잠금 — 프로그램이 만든 블록 변경을 **사용자 입력으로 읽지 않는다** (2026-08-24)

에뮬레이터 검증 중에 잡았다. **서식이 생기기 전부터 있던 버그**이고, 서식 기능이 그걸 드러낸 것뿐이다.

**증상**

```
AAAAA BBBBB          ← 한 문단
  ↓ 가운데에 목록을 끼운다
[text "AAAAA "] [list] [text "BBBBB"]     insertList가 커서를 2번 블록으로 옮긴다
  ↓ 그 상태에서 서식(빨강)을 건다
[text "AAAAA " 🔴빨강] [list] [text "BBBBB"]   ← **앞 문단에 걸렸다**
```

**원인**

블록을 프로그램으로 쪼개면 원래 입력창의 `value`가 짧아진다(`"AAAAA BBBBB"` → `"AAAAA "`).
**RN은 그때도 `onSelectionChange`를 쏜다.** 그 보고를 그대로 믿으면 방금 옮겨 둔 `caretRef`가
도로 앞 블록으로 끌려간다. 사용자는 손가락 하나 대지 않았는데 커서가 움직인 것으로 처리된다.

**고친 방법** — `caretLockedRef`

`onCaretChange`에 `reason`을 붙여 셋을 구분한다.

| reason | 뜻 | 처리 |
|---|---|---|
| `focus` | 사용자가 칸을 **직접 잡았다** | 커서 갱신 + **잠금 해제** |
| `program` | 편집기가 스스로 옮겼다(이미지 삭제) | 커서 갱신 + **잠금** |
| `selection` | 선택 영역이 바뀌었다 | **잠겨 있으면 무시** |

사진·목록·서식이 블록을 쪼갤 때 잠그고, 사용자가 아무 칸이나 **다시 잡을 때만** 풀린다.

⚠ **처음엔 *"포커스를 가진 칸의 보고만 받는다"* 로 고쳤는데 안 됐다.** 목록을 끼우면 포커스가
목록 항목으로 가는데 그건 텍스트 블록이 아니라서 추적값이 **0번에 낡은 채 남았고**, 그 낡은 값이
가드를 그대로 통과했다. 기준은 *"지금 포커스가 어디냐"* 가 아니라
**"사용자의 `focus` 이벤트가 다시 왔느냐"** 다.

**왜 이전 검증이 못 찾았나**

`check:diary-format` 28개는 **순수 계층**이다 — `splitParagraph`·`normalizeBlocks`에 배열을 넣고
배열을 받는다. 이 버그는 그 아래도 위도 아닌 **RN의 네이티브 이벤트 타이밍**에 있어서,
순수 계층 검사로는 원리적으로 못 잡는다. 여기에 가드를 억지로 만들지 않는다 —
**만들 수 있는 척하는 검사가 없는 검사보다 나쁘다.** 이 경로는 실기기·에뮬레이터에서만 확인된다.

⚠ 그리고 **화면만 봐서도 못 잡는다.** 서식이 없던 시절에는 이 버그가
*"두 번째 사진이 이상한 데 들어간다"* 로만 나타나는데, 사진 위치는 원래 헷갈리는 것이라
사용자도 우리도 오조작으로 넘긴다. **서식이 색을 입혀주고 나서야 눈에 보였다.**

**형제 훑기** — 같은 자리를 전수 조사했다. 블록을 쪼개거나 지우면서 커서를 옮기는 곳은 넷이고
**전부 잠근다**: `insertImageAtCaret` · `insertList` · `applyFormat` · `removeBlock`.

## 1.2 이미지

- 사용자가 고른 사진을 **앱 전용 디렉터리로 복사해서 보관**한다. 갤러리 URI만 참조하지 않는다.
  > 참조만 하면 사용자가 갤러리에서 원본을 지우거나 정리했을 때 **일기가 통째로 깨진다.**
  > 일기는 오래 남는 기록이라 외부 파일의 수명에 의존하면 안 된다.
- DB에는 **파일명(앱 디렉터리 기준 상대 경로)만** 저장한다. 절대 경로를 저장하지 않는다.
  > iOS·Android 모두 앱 업데이트·재설치 시 앱 컨테이너의 **절대 경로가 바뀐다.**
  > 절대 경로를 넣어두면 어느 날 모든 이미지가 한꺼번에 깨진다.
- 조각을 삭제하면 이미지도 소프트 삭제한다. **실제 파일은 아직 지우지 않는다** —
  ~~백업 착수 시 정한다~~(사진 백업이 붙어 조건이 만료됐다). 새 조건은
  [`BACKUP_SYSTEM.md`](./BACKUP_SYSTEM.md) §5.5 ⑤: **`blob_state='backed_up'`이던 파일만**
  지울 수 있고, 그것도 사진 백업이 실사용 데이터로 검증된 뒤다. 복원이 고아를 대량 생산하므로
  지금 켜면 **서버에 사본이 없는 사진이 전부 영구 삭제**된다.

**축소·압축 (2026-08-09 구현)**

`saveImage`가 복사 **전에** 긴 변 **1600px**로 줄이고 JPEG **0.8**로 굽는다
(`features/diary/api/image-store.ts`의 `MAX_EDGE`·`COMPRESS`).

⚠ **백업보다 먼저 넣었다.** 백업이 E2EE라 **서버가 사진을 줄일 수 없다** — 서버에 닿을 땐 이미
암호문이다(CLAUDE.md §5.1). 기기에서, 암호화 전에 줄이는 것 말고는 방법이 없고, 나중에 넣으면
그 전에 저장된 사진들은 원본 크기로 남는다. 되돌릴 수 없는 종류의 지각이라 앞당겼다.

지킨 것:

- **실패하면 원본을 그대로 쓴다.** 사진을 못 줄인 것보다 사진을 잃는 것이 훨씬 나쁘다.
  (네이티브 모듈이 없는 구버전 빌드에서도 이 폴백 덕에 깨지지 않는다.)
- **1600 이하면 손대지 않는다.** 이미 작은 사진을 다시 구우면 화질만 깎이고 용량은 안 준다.
- **확장자는 줄인 뒤 URI에서 뽑는다.** 결과는 JPEG인데 원본이 PNG·HEIC였을 수 있다 —
  원본 확장자를 붙이면 내용과 이름이 어긋난 파일이 남는다.
- **DB의 width·height도 줄인 뒤 값으로 넣는다.** 실제 파일과 어긋나면 레이아웃이 틀어진다.
- **피커에서는 압축하지 않는다**(`quality: 1`). 피커에서 굽고 저장할 때 또 구우면 화질만 두 번 깎인다.

⏭ 장수 제한은 아직 없다. **쿼터로 대신하고 있다** — 금고 하나가 2GB이고 초과하면
   업로드가 막힌다(`BACKUP_SYSTEM.md` §5.5). 장당 상한이 필요해지는 건 그 벽에
   실제로 닿는 사용자가 나온 뒤다.

**삽입 위치 (2026-08-08 구현)**

사진은 **커서가 있던 자리**에 들어간다. 그 텍스트 블록을 커서 기준으로 앞뒤로 쪼개고 사이에
이미지 블록을 끼운다. 항상 맨 끝에 붙이면 §1의 "본문 중간 원하는 위치에 삽입"이 성립하지 않는다.

- 사진을 고르는 동안 입력창은 포커스를 잃으므로, **마지막 커서 위치를 기억**해 두었다가 쓴다.
- 커서를 한 번도 두지 않았으면 맨 끝에 붙인다.
- 삽입 후 커서는 **새로 생긴 사진 아래 텍스트 블록**으로 옮긴다. 사진을 연달아 넣으면 넣은 순서대로 쌓인다.
- 사진 뒤에는 항상 빈 텍스트 블록이 따라온다 — 이어 쓸 자리가 없으면 글이 사진에서 끊긴다.
  이때 생기는 빈 블록은 저장 시 `normalizeBlocks`가 정리한다.

## 2. 하루에 몇 개까지 쓰는가

~~DB는 제한하지 않고 UI가 "하루 하나"를 유도한다(하루 여러 개 허용)~~
→ **정정(2026-08-08, 사용자 결정): 하루에 조각은 하나다.**

| 층 | 규칙 |
|---|---|
| DB | `entry_date`에 UNIQUE 제약을 **걸지 않는다** (아래 이유) |
| 저장소 | `createDiary`·`updateDiary`가 **트랜잭션 안에서** 같은 날짜의 살아있는 조각을 확인하고 막는다 |
| UI | 날짜 시트에서 이미 쓴 날은 **점이 찍힌 채 눌리지 않는다**. 아직 안 온 날과 색을 다르게 죽인다 |

**왜 DB UNIQUE가 아닌가.** 나중에 다른 기기의 백업을 복원할 때 같은 날짜가 부딪히면
**복원 전체가 실패**한다. 그건 사람이 "어느 쪽을 남길지" 고를 문제이지 INSERT가 죽을 문제가 아니다.
소프트 삭제(§7) 때문에 필요한 제약이 "부분 UNIQUE(`WHERE deleted_at IS NULL`)"라는 점도
마이그레이션·복원 양쪽에서 다루기 번거롭다. 규칙은 **저장소 계층**이 지키고, 데이터 모델은 열어둔다.

**날짜로 푼다 — 버튼을 나누지 않는다** (2026-08-08 결정).

홈 버튼도 하단 ⊕도 언제나 *조각 쓰기* 하나이고 **항상 작성 화면**을 연다.
오늘 썼는지에 따라 목적지를 바꾸면(예: 상세로 보내기) **지난 날짜로 쓰러 들어갈 문이 사라진다**
— 실제로 그렇게 만들었다가 되돌렸다. 대신 **작성 화면이 날짜를 정한다**:

| 오늘 조각 | 작성 화면이 여는 모습 |
|---|---|
| 없다 | 날짜 = **오늘**. 대부분은 오늘 걸 쓰러 오므로 아무것도 묻지 않는다 |
| 있다 | 날짜 **미선택**(`날짜를 골라주세요`) + 날짜 시트가 먼저 열린다. 저장 버튼은 죽어 있다 |

날짜를 못 고른 채로는 저장할 수 없다. 시트에서 이미 쓴 날은 눌리지 않으므로,
**고르는 순간 그 날짜는 반드시 비어 있다** — 다 쓰고 나서 막히는 일이 생기지 않는다.
저장소 확인은 최후 방어이고, 사용자가 볼 일이 없어야 정상이다.

## 3. 날짜 규칙

- `entry_date`는 `YYYY-MM-DD` 문자열이며 **기기 로컬 타임존 기준**이다.
- 새 조각의 기본값은 **오늘**이되, **사용자가 날짜를 바꿀 수 있다.**
- 🚫 "새벽 N시 이전은 전날로 친다" 같은 보정은 **하지 않는다.** 규칙이 숨어 있으면 사용자가 캘린더를
  볼 때 혼란스럽고, 날짜를 직접 바꿀 수 있으므로 실익이 없다.
- 타임존이 바뀌어도(해외 이동) 이미 저장된 `entry_date`는 재계산하지 않는다 — 쓴 사람이 그날이라고
  생각한 날짜가 진실이다.
- **미래 날짜는 고를 수 없다** (2026-08-08 결정 → 잠시 해제 → **재확정**, 사용자 결정).
  일기는 지나간 하루의 기록이다. 날짜 선택 UI가 `maxDate = 오늘`로 막는다 —
  **DB 제약은 걸지 않는다**(§2와 같은 이유: UI가 유도하고 데이터 모델은 열어둔다).
- 날짜 변경 UI는 `components/DatePickerSheet`(하단 시트) + `components/MonthGrid`(월 격자)다.
  캘린더 탭도 같은 격자를 쓴다 — 두 벌을 만들면 '오늘 표시'나 첫 요일 규칙이 언젠가 서로 어긋난다.

## 4. 감정

- 고정 코드 목록을 쓴다. DB에는 **코드 문자열**을 저장한다(정규화 테이블 없음 — 로컬 단일 사용자라 이득이 없다).
- 감정은 **선택**이다. 고르지 않으면 `NULL`.
- 목록을 늘릴 때는 **코드를 추가만** 한다. 기존 코드의 의미를 바꾸거나 지우지 않는다 —
  이미 저장된 조각이 의미를 잃는다. (Expand-only)
- ⚠ 초기 목록은 디자인 시안에 맞춰 조정될 수 있다. 코드 값은 영문 소문자 스네이크로 고정하고,
  표시 라벨만 바꾸는 구조로 둔다.

## 5. 연속 작성일 (streak)

`entry_date`의 **서로 다른 날짜** 기준으로 센다(하루에 3개를 써도 1일).

| 상황 | streak |
|---|---|
| 오늘 썼다 | 오늘부터 과거로 끊기지 않고 이어진 날 수 |
| 오늘 아직 안 썼다 | **어제까지의 연속 일수를 유지해서 보여준다** |
| 어제도 안 썼다 | 0 |

**왜 오늘 안 썼다고 0으로 떨어뜨리지 않는가.** 아침에 앱을 열었을 때 "0일"이 보이면 이어온 기록이
사라진 것처럼 느껴진다. 아직 오늘이 끝나지 않았으므로 끊긴 게 아니다. 오늘이 지나도록 안 쓰면
다음 날 자연히 0이 된다.

- 삭제된 조각(`deleted_at IS NOT NULL`)은 세지 않는다.

## 6. 검색

**제목·본문 평문·태그**를 부분 문자열로 검색한다(`LIKE '%키워드%'`). FTS5는 쓰지 않는다.

- 본문은 블록 JSON이 아니라 **파생 평문 컬럼**을 검색한다(§1.1) — JSON을 긁으면 `"type"` 같은
  구조 문자열이 걸린다.
- 태그는 정확히 일치하지 않아도 걸리게 한다(`여행` 검색에 `여행기록`도 나온다).
- 같은 조각이 제목·본문·태그 여러 곳에서 걸려도 결과에는 **한 번만** 나온다.

- 이유: SQLite FTS5의 기본 토크나이저는 한국어를 어절 단위로만 쪼갠다. "행복했던"을 저장해두고
  "행복"으로 찾으면 안 걸린다. 한국어 부분 문자열 검색에는 실질적으로 `LIKE`가 맞다.
- 규모: 하루 1~3개면 10년을 써도 1만 건 남짓이다. 이 규모에서 `LIKE` 스캔은 체감되지 않는다.
- 재검토 시점: 조각이 수만 건이 되거나 검색이 느려진다는 신호가 오면 그때 FTS5 + 한국어
  토크나이저(예: trigram)를 다시 본다. **지금 넣으면 복잡도만 늘고 이득이 없다.**
- 검색은 삭제된 조각을 제외한다. 대소문자 구분은 하지 않는다(영문 입력 대비).

## 7. 삭제 — 소프트 삭제

**하드 삭제하지 않는다.** `deleted_at`에 시각을 기록한다.

- **이유는 백업이다.** 하드 삭제하면 나중에 클라우드 백업/복원을 붙였을 때 "이 조각이 원래 없었던
  것인지, 지운 것인지"를 구분할 수 없어 **지운 일기가 다른 기기에서 되살아난다.** 묘비(tombstone)가 필요하다.
- 조회·검색·캘린더·streak는 모두 `deleted_at IS NULL`만 본다.
- 사용자에게는 즉시 사라진 것으로 보인다. MVP에 휴지통 UI는 없다.
- 묘비를 언제 실제로 지울지(보관 기간)는 백업 착수 시 정한다 — [`ARCHITECTURE.md`](./ARCHITECTURE.md) §8.

## 8. 수정

- `content`·`title`·`emotion`·`entry_date`를 바꿀 수 있다.
- 수정 시 `updated_at`을 갱신한다. **백업 동기화가 이 값으로 최신본을 판단**하므로 빠뜨리면 안 된다.
- 수정 이력(버전)은 남기지 않는다 — MVP 범위 밖.

**수정은 상세 화면 제자리에서 한다** (2026-08-08 결정). 별도 화면을 띄우지 않는다 —
읽던 글을 고치는데 화면이 아래에서 덮고 올라오면 다른 데로 이동한 것처럼 느껴진다.

- 편집기는 `features/diary/components/DiaryEditor` **컴포넌트**다(화면이 아니다).
  새 조각은 `app/write`가 모달로 띄우고, 기존 조각은 상세 화면이 같은 편집기를 제자리에 끼운다.
- 수정 중 안드로이드 뒤로가기는 **화면을 닫지 않고 수정을 취소**한다.
- 저장하면 읽기 모드로 돌아오며 상세 내용을 다시 읽는다.

## 8.1 저장·수정·삭제는 확인을 받는다 (2026-08-10 사용자 결정)

~~저장은 누르면 바로 저장, 삭제만 확인~~ → **세 동작 모두 확인창을 거친다.**

| 동작 | 확인 문구 | 실행 버튼 |
|---|---|---|
| 새 조각 저장 | `write.confirmSaveTitle` · `Body` | `common.save` |
| 수정 저장 | `write.confirmUpdateTitle` · `Body` | `common.save` |
| 삭제 | `detail.deleteTitle` · `Body` (기존) | `detail.deleteConfirm` (destructive) |

⚠ **저장 확인은 CLAUDE.md 기둥 1(쓰기 마찰 최소화)과 맞바꾼 것이다.** 조각 하나를 남기는 데
탭이 하나 늘어난다. 그럼에도 넣은 이유는 수정 저장이 **옛 내용을 되돌릴 수 없게 덮어쓰기** 때문이고,
새 조각도 같은 흐름으로 두어야 "어떤 저장은 묻고 어떤 저장은 안 묻는" 예측 불가가 안 생긴다.

- 확인창은 **저장 직전**에만 세운다. 광고·이미지 정리 등 뒤따르는 처리는 순서를 바꾸지 않는다(§7).
- 취소하면 편집 상태가 그대로 남는다 — 되돌아와서 이어 쓸 수 있어야 한다.
- ⏭ 마찰이 실제로 거슬리면 **새 조각 저장만** 확인을 빼는 것이 첫 번째 후퇴 지점이다.
  (덮어쓰기가 없는 쪽이라 잃을 게 없다.)

### 상세 헤더 버튼 (2026-08-10 변경)

~~[휴지통] [연필+"수정" 글자 버튼]~~ → **[연필] [휴지통]** — 둘 다 아이콘만, 자리를 맞바꿨다.

⚠ **삭제가 오른쪽 끝, 엄지가 가장 쉽게 닿는 자리로 왔다.** 되돌릴 수 없는 동작이 가장 누르기 쉬운
자리에 있는 셈이라, 확인창(§8.1)이 이제 형식이 아니라 **실질적인 안전장치**다. 확인창을 걷어내는

## 8.2 첫 화면 — 조각이 0개일 때 (2026-08-23)

**온보딩 화면을 세우지 않는다.** 기둥 1(쓰기 마찰 최소화)과 정면으로 부딪힌다 — 일기를 쓰러
들어온 사람에게 3장짜리 안내를 먼저 보이는 것은 문을 하나 더 다는 일이다.
대신 **홈의 빈 상태 한 화면이 그 역할을 한다.**

레퍼런스(Linear · Notion · Mobbin 계열 모바일 empty state)에서 공통으로 나오는 규칙 셋만 가져왔다:

| 규칙 | 적용 |
|---|---|
| **없는 목록의 제목을 세우지 않는다** | 🔴 `최근의 조각들` 헤더를 `recent.length > 0`으로 감쌌다. 빈 목록 위의 제목은 *"뭔가 있어야 하는데 없다"* 로 읽힌다 — 고장 난 화면처럼 보인다 (`더보기`는 이미 조건부였다) |
| **모바일 빈 상태는 가운데로** | 카드(좌측 정렬 박스)를 **벗기고** 중앙 정렬 + 조용한 아이콘(Lucide `Feather`, `accentMuted`) |
| **CTA는 하나** | 🚫 빈 상태에 버튼을 넣지 않는다. 위에 이미 `조각 쓰기`가 있고, 둘을 두면 둘 다 약해진다 |

🔴 **본문 문구를 CTA에서 설명으로 바꿨다.**

```
전   아직 모은 조각이 없어요 / 오늘의 첫 조각을 남겨보세요.     ← 위 버튼과 같은 말
후   아직 모은 조각이 없어요 / 하루에 하나씩 짧게 남기면, 나중에 모아서 돌아볼 수 있어요.
```

옛 문구는 바로 위 버튼의 반복이라 **한 줄을 쓰고 아무것도 말하지 않았다.** 온보딩이 없으므로
이 한 줄이 앱의 약속(**하루 하나 · 짧아도 된다 · 나중에 회고**)을 말하는 유일한 자리다.
⚠ 15개 언어에서 이걸 CTA로 되돌리지 않게 번역 지시에 명시했다 — 직역하면 *"Write your first one!"* 로 돌아간다.

⚠ **카드를 벗긴 것은 여기뿐이다.** 목록에 조각이 하나라도 있으면 카드로 그린다 — 빈 상태의
문제는 *테두리 안이 비어 있는 것*이지 카드 자체가 아니다.

## 8.3 🔴 개발용 일기 시드 — 복원으로 넣지 않는다 (2026-08-25)

리포트 시각화(요일 격자·주별 막대·월별 히트맵)와 계층 요약을 **화면에서** 보려면 여러 달치
조각이 필요한데, 손으로 넣으면 하루 한 건씩 수백 번을 눌러야 한다.

### ~~백업 복원으로 넣는다~~ → 🚫 안 한다

제안됐고, 조사해 보니 **기술적으로는 가능하지만 가장 비싸고 위험한 길**이었다.

| | |
|---|---|
| 🔴 **기존 일기가 전멸한다** | `restore.ts`가 `diaries`·`tags`·`diary_tags`·`diary_images`·`ai_reports`를 **`DELETE` 후 다시 넣는다.** 병합이 아니다 |
| 🔴 **SecureStore 비밀을 덮어쓴다** | `adoptBackupSecret()`. 실기기에 가짜 복구 코드를 넣으면 **그 사람의 진짜 백업이 영영 안 열린다** |
| 필요한 것이 많다 | 로그인 세션 + 로컬 Supabase 스택 + 서버 기동 + 봉인 스크립트. ⚠ 구독 `pro`는 **불필요**하다(읽기는 구독을 안 본다) |
| 얻는 것 | 사진 blob까지 포함한 실전 경로 검증 — **복원 자체를 시험하려는 게 아니면 값이 없다** |

⚠ 매니페스트(`MANIFEST_FORMAT` 3)와 봉투(XChaCha20-Poly1305 + HKDF)는 **순수 계층이라
Node에서 만들 수 있다**(`check:backup-crypto`가 이미 그렇게 돈다). 막는 것은 암호가 아니라
**전체 교체라는 성질**이다.

### 대신 — SQLite에 직접 심는다 (`features/dev/seed-diaries.ts`)

`features/backup/api/device-check.ts`가 이미 쓰던 방법이다. 서버·암호·네트워크 0.

```
설정 › DEV › 더미 일기 심기 (작년 1월 ~ 어제)
설정 › DEV › 심은 일기만 지우기
```

| 지키는 것 | 어떻게 |
|---|---|
| **기존 조각을 안 건드린다** | `seed-` 접두사가 **아닌** 조각이 있는 날짜는 건너뛴다. `createDiary()`가 막는 *날짜당 1건*을 원시 INSERT로 우회하면서도 그 규칙을 깨지 않는다 |
| **되돌릴 수 있다** | `id LIKE 'seed-%'`만 지운다 |
| **결정적이다** | `Math.random()`을 안 쓰고 날짜에서 값을 유도한다 — 두 번 심으면 같은 내용이라 화면 비교가 흔들리지 않는다 |
| **진짜처럼 생겼다** | 약 20%는 **빈 날**로 남기고(안 그러면 격자·히트맵이 거짓말처럼 보인다), 길이를 1줄~6줄로 크게 흔들고(§10.3에서 코퍼스가 전부 짧아 겪은 일), 10%쯤은 **서식**을 넣는다(§1.1) |

⚠ **`__DEV__` 안에서만 돈다.** 함수 자체가 아니면 `throw`하고, 설정의 두 줄도 `__DEV__` 블록
안이라 릴리스 번들에서 통째로 접힌다.

🔴 **Play 서명 실기기에서는 못 쓴다.** `__DEV__`가 `false`라 DEV 섹션이 사라지고, dev 빌드는
서명이 충돌해 나란히 깔 수도 없다(`CLAUDE.md` §12 2026-08-24). 실기기에 데이터를 넣으려면
`com.son0925.jogak.dev` 같은 **별도 패키지 변형**이 필요하다(`app.config.js`의 `APP_VARIANT`가
이미 쓰는 수법). ⏭ 필요해지면 그때 만든다.
