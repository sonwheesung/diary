# ARCHITECTURE — 서버 경계와 신원

> 조각이 어떤 서버에 무엇을 맡기는가. **이 경계를 어기면 되돌리기가 가장 비싸다.**
> 원칙 요약은 [`../CLAUDE.md`](../CLAUDE.md) §5. 이 문서가 상세 정본이다.

## 1. 전체 그림

```
                          ┌─────────────────────────────┐
                          │  common_server (배포됨)      │
   조각 앱 ──HTTPS──────▶ │  https://common-server       │
   (Expo)                 │        .vercel.app           │
     │                    │  공지 · 문의 · 신원(subject)  │
     │                    │  · 엔타이틀먼트(구독·광고제거) │
     │                    │  Supabase `common-server`    │
     │                    └─────────────────────────────┘
     │                                  ▲
     │                                  │ 같은 서버를 my_word · (추후 배구)도 사용
     │
     │                    ┌─────────────────────────────┐
     └──HTTPS───────────▶ │  조각 서버 (미생성)           │
                          │  일기 백업/복원 · AI 리포트    │
                          │  Supabase 조각 전용           │
                          └─────────────────────────────┘

   로컬 (진실의 원본)
   expo-sqlite ── 일기 본문 · 감정 · 작성일
```

**일기 본문의 진실은 기기다.** 조각 서버가 갖는 것은 백업 사본이다. 서버가 죽어도 앱은 정상 동작해야 한다.

## 2. 왜 조각 데이터를 common_server에 넣지 않는가 (2026-08-07 결정)

### 2.1 개인정보 등급이 다르다

common_server는 "개인정보 최소수집"을 **명시적 설계 원칙**으로 박아뒀다 —
문의에 저장하는 기기정보는 platform·appVersion 뿐이고, IP는 레이트리밋 키로만 쓰고 버린다
(common_server `CLAUDE.md` "규약"). 여기에 일기 본문을 넣는 순간:

- 그 원칙이 무너진다. 처리방침·보관기간·파기 정책이 전부 다른 등급이 된다.
- my_word·배구의 문의 데이터와 남의 **일기 본문**이 같은 DB에 공존한다.
- 유출 시 파급이 앱 전체로 번진다.

**한 번 섞이면 분리 마이그레이션은 매우 비싸다.** 처음부터 나눈다.

### 2.2 배포와 장애 반경이 묶인다

common_server는 **1배포 N앱**이다(앱 코드가 요청 파라미터로 온다). 따라서:

- 조각 스키마를 고칠 때마다 my_word·배구가 쓰는 배포를 건드리게 된다.
- common_server가 죽으면 조각 백업까지 같이 죽는다.
- 반대로 조각의 트래픽·AI 부하가 다른 앱의 공지·문의 응답을 갉아먹는다.

### 2.3 워크로드 성질이 다르다

AI 요약은 LLM 호출 비용·큐잉·긴 실행시간이 붙는다. 공지·문의 같은 짧은 CRUD 서버리스 함수와
같은 배포에 둘 성질이 아니다(타임아웃·동시성·비용 모델이 전부 다르다).

## 3. 무엇을 어디에 두는가

| 데이터 | 위치 | 이유 |
|---|---|---|
| 일기 본문 · 감정 · 작성일 | **기기(expo-sqlite)** | 진실의 원본. 오프라인 동작 |
| 일기 백업 사본 | **조각 서버 DB — 암호문만** | 구독자 전용. 서버는 복호화 불가(§6) |
| 암호화 키 | **기기(SecureStore) + 사용자 복구 코드** | 서버는 갖지 않는다(§6.3) |
| AI 요약 리포트 | **기기(expo-sqlite)** | 리포트에도 일기 요약이 들어간다 — 서버에 남기지 않는다(§6.2) |
| 공지사항 | **common_server** | 앱 무관 브로드캐스트 |
| 문의 | **common_server** | 앱 무관. 관리자 콘솔이 이미 있음 |
| 신원(subject) · 구글 로그인 | **common_server** | 단일 진실. §4 |
| 구독·광고제거 엔타이틀먼트 | **common_server** | RevenueCat 웹훅이 여기로 옴(PLAN Phase 9) |
| 읽은 공지 id | **기기(AsyncStorage)** | 서버에 읽음 API 없음(common_server 설계) |
| PIN · 생체인증 설정 | **기기(SecureStore)** | 서버로 절대 보내지 않음 |

## 4. 신원 — common_server가 단일 진실

### 4.1 규칙

**로그인은 common_server가 담당한다. 조각 서버는 토큰을 검증만 한다.**

```
1. 앱: 구글 로그인 → 구글 ID 토큰 획득
2. 앱 → common_server: ID 토큰 제출 → 검증 후 subject 생성/조회 → 서명 토큰 발급
3. 앱: 서명 토큰을 SecureStore에 보관
4. 앱 → 조각 서버: Bearer <서명 토큰>
5. 조각 서버: 토큰 서명 검증 → subject_id 추출 → 그 값으로 백업 행을 찾는다
```

- 조각 DB의 `subject_id`는 **FK가 아니다**. DB가 다르므로 참조 무결성을 걸 수 없다.
  대신 "토큰 검증에 성공한 subject_id만 쓴다"는 규약으로 지킨다.
- 구독 여부는 common_server 엔타이틀먼트가 진실이다. 조각 서버가 매 요청 조회하지 않도록
  **토큰 클레임에 실어 보내되 TTL을 짧게** 두는 방식을 검토한다(환불·해지 반영 지연 때문).

### 4.2 조각이 자체 로그인을 만들면 안 되는 이유

신원이 두 곳(common의 subject vs 조각의 자체 계정)에 생기면:

- "이 구독자가 저 백업의 주인인지"를 매칭할 방법이 없다. 엔타이틀먼트는 common에 있는데
  백업은 조각 계정에 매달려 있기 때문이다.
- 앱이 4~5개로 늘 때마다 로그인 구현이 반복된다.
- 계정 삭제 요청(개인정보 파기)을 두 곳에 나눠 처리해야 한다.

### 4.3 ⚠ 현재 common_server에는 신원이 없다

common_server v1은 **신원 개념이 아예 없다**. 공지는 읽기 전용 브로드캐스트, 문의는 익명 단방향이다.
`docs/PLAN.md` §8 **Phase 7**(`subjects` 테이블 + `POST /api/v1/devices` 토큰 발급 + `tickets.subjectId`)이
들어와야 로그인·쿠폰·광고제거·문의답변이 **한꺼번에** 열린다.

즉 **조각은 common_server Phase 7의 첫 소비자**가 된다. 조각의 로그인·문의(로그인 필수)·구독·백업이
전부 여기에 막혀 있다.

또한 common_server는 **Expand-only** 규약이다 — 기존 컬럼을 바꾸거나 지우지 않고 덧붙인다.
조각 때문에 my_word가 쓰는 계약을 깨지 않는다.

## 5. common_server 연동 계약 (v1 현재)

베이스 URL: `https://common-server.vercel.app` · 조각의 `app_code`: `jogak` (**아직 미등록**)

| 엔드포인트 | 용도 | 호출 시점 |
|---|---|---|
| `GET /api/v1/bootstrap?app=jogak` | 점검·버전게이트·공지 | **앱 부팅 시 1회** |
| `POST /api/v1/tickets` | 문의 접수(익명 단방향) | 사용자가 문의 전송 |

### 반드시 지킬 것 (common_server 핸드오프 규약 승계)

1. **bootstrap 실패로 앱을 막지 마라.** 네트워크 오류·서버 다운·타임아웃이면 평소대로 쓰게 둔다.
   점검·강제업데이트 게이트는 **조회에 성공했을 때만** 적용한다.
2. **bootstrap은 부팅 시 1회.** 화면 전환마다 부르지 않는다.
3. **개인정보를 더 보내지 마라.** 문의에 실리는 기기정보는 platform·appVersion 뿐이다.
   기기 식별자·osVersion·사용자 이름을 추가로 싣지 않는다.
4. **SDK는 복사해서 쓴다.** `common_server/client/{index.ts,types.ts}` → `lib/common-server/`.
   monorepo·npm 패키지 안 쓴다. 복사 시점을 파일 상단 주석에 남긴다.
5. **`EXPO_PUBLIC_*`는 빌드 시점에 번들로 인라인된다.** `.env`를 바꾸면 재빌드해야 반영된다.
6. 미등록·비활성 앱은 **404**다. `jogak`을 `apps` 테이블에 등록하기 전에는 공지·문의가 동작하지 않는다.
   등록 명령: `node tools/seed.ts jogak "조각"` (common_server 쪽에서 실행)

## 6. 암호화와 AI 처리 경로 (2026-08-07 결정)

### 6.1 충돌과 해법

두 요구가 정면 충돌했다 — **백업은 암호화하고 싶고, AI 요약은 본문을 읽어야 한다.**
서버가 *저장물을* 읽는 대신, **앱이 로컬 평문을 그때만 흘려보내는** 구조로 푼다.
사용자는 어차피 일기를 읽으려면 기기에서 복호화하므로, 평문은 항상 기기에 존재한다 — 그 사실을 이용한다.

```
백업:      앱(로컬 평문) ──암호화──▶ 조각 서버 ──▶ 암호문만 보관 (서버 복호화 불가)
AI 리포트: 앱(로컬 평문) ─────────▶ 조각 서버(프록시·무저장) ──▶ LLM ──▶ 리포트 ──▶ 앱 로컬 저장
```

**얻는 것**: 서버에 상시 축적된 읽을 수 있는 일기 더미가 사라진다. DB가 통째로 유출돼도 읽을 게 없다.
유출 리스크에서 가장 큰 표적이 없어지는 것이 이 설계의 핵심 이득이다.

**⚠ 얻지 못하는 것**: 본문은 **여전히 우리 서버를 통과한다**(리포트 생성 순간). 달라지는 건
"통과하되 저장하지 않는다"이다. 따라서 **"우리는 절대 볼 수 없습니다"는 거짓말**이고,
정확한 표현은 **"저장하지 않습니다"** 다. 이걸 흐리게 쓰면 나중에 가장 크게 터진다.

### 6.2 결정 표

| 항목 | 결정 |
|---|---|
| 백업 | 클라이언트 암호화(E2EE) |
| 암호화 키 | 기기 SecureStore + 사용자 복구 코드 1회 발급. **서버 미보유**(§6.3) |
| AI 리포트 | 앱이 로컬 평문 → 조각 서버 프록시 → LLM. **서버 무저장** |
| 리포트 저장 | **로컬**. 백업에 암호화되어 포함. 리포트에도 일기 요약이 들어가므로 서버에 남기면 논리가 깨진다 |
| 생성 트리거 | 앱에서 사용자 트리거 |
| 범위 | **주간부터**. 단가 확인 후 월간 → 연간 |
| 월간·연간 생성 | **계층 요약** — 주간 리포트를 입력으로 월간, 월간을 입력으로 연간 |

### 6.3 왜 클라이언트가 LLM을 직접 부르지 않는가

**LLM API 키를 앱 번들에 넣을 수 없다.** 즉시 추출되어 남이 우리 키로 API를 긁고 요금은 우리가 낸다.
그래서 반드시 조각 서버가 프록시한다. 부수 이득으로 **구독자 게이트·호출 캡·비용 통제**가 가능해진다
(클라이언트 직접 호출이었다면 전부 불가능).

### 6.4 따라오는 제약 — 서버 배치 생성 불가

서버에 본문이 없으므로 **"일요일 밤에 리포트를 미리 만들어두고 월요일 아침에 푸시"가 불가능하다.**
앱이 열려 있을 때 클라이언트가 트리거해야 한다.

→ UX는 "월요일에 앱을 열면 *지난주 조각 리포트가 준비됐어요* 카드가 뜨고 거기서 생성"이 된다.
기대감을 만드는 연출로 쓸 수 있어 손해로 보지 않는다. 다만 **푸시로 리포트 완성을 알리는 기획은 불가능**하다.

### 6.5 암호화 키 — 채택 근거

| 안 | 판단 |
|---|---|
| 기기에만 저장, 복구 수단 없음 | 🚫 **자기모순**. 기기를 잃었을 때 쓰라고 만든 백업인데 기기를 잃으면 키도 잃는다 |
| 사용자 비밀번호에서 키 유도 | 🚫 구글 로그인만 쓰기로 해놓고 비밀번호를 하나 더 요구 — 기둥 1(쓰기 마찰 최소화)과 충돌 |
| 서버가 키 보관 | 🚫 E2EE가 아니게 되어 §6.1 전체가 무의미 |
| **기기 SecureStore + 복구 코드 1회 발급** | ✅ **채택** |

- 흐름: 백업을 켤 때 앱이 랜덤 데이터 키 생성 → SecureStore 보관 → 사용자에게 복구 코드 1회 표시.
  새 기기에서는 구글 로그인 → 암호문 수신 → 복구 코드 입력 → 복호화.
- 약점("사용자가 복구 코드를 안 적어두면 결국 못 푼다")은 **설정에서 복구 코드를 언제든 다시 볼 수 있게** 해서 완화한다
  (기기에 키가 살아 있는 동안은 재발급 없이 조회 가능). 무료 기능인 JSON 내보내기가 최후 안전망이다.
- **복구 코드 분실 = 복원 불가임을 백업 활성화 화면에서 명시한다.** CS로 와도 해줄 방법이 없다.

### 6.6 반드시 지킬 것

1. **백업을 켜지 않은 사용자의 일기는 서버로 단 한 글자도 가지 않는다.**
2. **프록시는 요청 본문을 로그에 남기지 않는다.** 에러 로깅·관측(Sentry 등)에 본문이 섞이는 것이
   가장 흔한 유출 경로다. 프록시 경로는 본문 로깅을 명시적으로 끈다.
3. **AI 요약을 위해 서버가 본문을 읽는다는 사실을 구독 화면에 명시한다.**
4. **연간 리포트에 원본 365개를 통째로 넣지 않는다.** 비용이 튀고 서사 품질도 떨어진다 — 계층 요약을 쓴다.

## 8. 열린 질문 (CLAUDE.md §12와 동일 — 착수 전 매듭)

- **백업 단위**: 전체 스냅샷 vs 증분. 기기 2대 복원 충돌 규칙.
- **암호화 구현 수단**: RN에서 AES-256-GCM을 무엇으로 돌릴지(expo-crypto는 해시·난수 중심).
  착수 시 공식 문서로 확인한다 — 기억으로 단정 금지(DOC_DISCIPLINE §6).
- **구독 상품 구성**: 광고 제거 + 백업 + AI를 단일 구독으로 묶을지.
- **LLM 제공자 처리위탁·국외이전 고지**: 처리방침에 명시 필요. `privacy-kr` 스킬 단계에서 확정.
