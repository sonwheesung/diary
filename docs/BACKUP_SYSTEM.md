## 1. 한 줄 요약

일기를 **기기에서 잠근 뒤** 서버에 올린다. 서버는 암호문과 메타데이터를 **저장하지만 읽지 못한다.**

```
로컬 DB → 매니페스트 → 파트 분할 → 봉인 → reserve → 서명 URL PUT → commit
로컬 DB ← 전체 교체  ← 병합    ← 개봉 ← 다운로드 ← 서명 URL     ← latest
```

### ⚠ 고지 문구 — AI와 정반대다

| | 정확한 표현 | 쓰면 안 되는 표현 |
|---|---|---|
| **백업** | **"우리는 읽지 못합니다"** | ~~"아무것도 저장하지 않습니다"~~ — 암호문과 메타데이터는 저장한다 |
| **AI 리포트** | **"저장하지 않습니다"** | ~~"볼 수 없습니다"~~ — 본문이 평문으로 프록시를 지나간다 |

**한 화면에 섞어 쓰지 않는다.** i18n 키도 `backup.notice.*` / `ai.notice.*`로 분리해 재사용을 막는다.

## 2. 키 — 복구 코드 하나에서 전부 유도된다

```
복구 코드 = 128비트 CSPRNG = 27자 (Crockford Base32 26심볼 + 체크심볼 1)
  ├─ DEK      = HKDF-SHA256(코드, "jogak/dek/v1",      32B)  ← XChaCha20-Poly1305 키
  ├─ vault_id = HKDF-SHA256(코드, "jogak/vault-id/v1", 16B)  ← 서버에서 금고를 찾는 이름
  └─ kid      = HKDF-SHA256(코드, "jogak/kid/v1",       4B)  ← 봉투 헤더의 키 식별자
```

**기기에 저장하는 것은 비밀 16바이트 하나뿐이다**(`jogak.backup.secret`, SecureStore).
나머지는 매번 유도한다 — 두 벌을 두면 어긋나고, 어긋나면 남의 금고를 조회하거나 못 여는 금고가 생긴다.

### 되돌릴 수 없는 결정 4개

사용자에게 발급한 값이거나 마이그레이션 경로가 없는 것들이다. **바꾸면 기존 사용자가 백업을 영영 못 연다.**

| # | 결정 | 왜 되돌릴 수 없나 |
|---|---|---|
| 1 | **코드 형식** — 128비트 · MSB-first · 하위 2비트 0 패딩 · 체크심볼 = **128비트 정수** mod 37 · 4자 6그룹 + 3자 | 종이에 적어둔 값이 앱과 달라진다 |
| 2 | **SecureStore 키 이름** `jogak.backup.secret` | SecureStore에 마이그레이션 개념이 없다 |
| 3 | **`vault_id` 표현** — 소문자 hex 32자 | DB 컬럼·서명 URL 경로·오류 코드가 전부 이 표현이다. 어긋나면 전 사용자 재업로드 |
| 4 | **HKDF info 문자열** — US-ASCII 바이트 그대로, NUL 종단·길이 접두 **없음** | 어긋나면 키가 통째로 달라지는데 **자기 왕복 테스트로는 100% 통과한다**(양쪽이 같은 코드를 쓰니까) |

### 왜 256비트가 아니라 128비트인가

256비트면 53자, 128비트면 27자다. 128비트는 무차별 대입으로 깨지지 않으므로(2^128) 실질
보안은 같고, **이 기능의 실제 실패 모드는 해독이 아니라 오타와 분실**이다. 손으로 옮겨 적는
글자 수를 절반으로 줄이는 쪽이 훨씬 크게 이긴다.

### ⚠ Extract를 건너뛸 수 없다 (설계 정정, 2026-08-11)

~~"입력이 이미 균일 랜덤이니 HKDF-Expand만 쓴다"~~ → **Extract + Expand.**
RFC 5869 §2.3이 *"PRK: a pseudorandom key of **at least HashLen** octets"* 를 요구해
16바이트 코드는 PRK 자리에 올 수 없다. "입력이 균일하다"는 **엔트로피** 얘기였고 길이 요건은
별개다 — Extract가 정확히 그 일(짧은 IKM → HashLen PRK)을 하라고 있는 단계다. salt는 비운다.

**KAT가 이걸 잡았다.** 자기 왕복만 돌렸으면 통과했을 오류이고, 다른 기기에서 복원할 때
처음 드러났을 것이다.

## 3. 봉투 v1

```
magic "JGKB" 4 | version 1 | suite 1 | flags 1 | kid 4 | type 1 | ctxLen 1 | context N | nonce 24
암호문 ‖ tag(16)
```

**헤더 전체가 그대로 AAD다.** 목적은 적대적 운영자가 아니라 **내 업로드 코드가 파일을
뒤바꾸는 사고를 소리 나게 만드는 것**이다 — 그렇게 적어두지 않으면 다음 사람이 서명 체인·
투명성 로그로 확장한다.

| 필드 | 값 | 근거 |
|---|---|---|
| `version` | `0x00~0x0F` **실험 구간**, 사용자 릴리스는 `0x10` 이상 | "초안"을 문서 표현이 아니라 **바이트로 강제**한다 |
| `suite` | `0x01` = XChaCha20-Poly1305 + HKDF-SHA256 | `0x00`은 예약이라 거부 |
| `flags` | bit0 = 키 래핑(KEK/DEK) **예약만** | ⚠ 켜는 순간 **Play E2EE 면제가 사라진다** — 키가 서버로 가는 설계라서다 |
| `ctxLen` | context 바이트 수 | 없으면 모르는 `type`에서 nonce 위치를 못 찾는다. 그래도 **모르는 type은 거부**한다 |
| `context`(manifest) | `seq u32 BE` + `genId 8B` + `part u16 BE` + `partCount u16 BE` | `seq`가 u32인 이유는 아래 |
| `context`(blob) | `sha256(암호문) 32B` | 2차(사진) |

### `genId`가 없으면 세대가 찢어진다

같은 `seq`로 재시도하는 동안 서버에 **옛 파트와 새 파트가 함께 남을 수 있다.**
`seq`도 `partCount`도 같아서 AEAD가 **전부 통과한다** — 조용한 데이터 손상이다.
세대마다 랜덤 8바이트를 헤더에 넣어 묶는다.

### `seq`가 u64가 아니라 u32인 이유

`DataView.getBigUint64`는 **BigInt**를 돌려주고, BigInt는 `JSON.stringify`가 **throw한다.**
`seq`가 매니페스트 JSON이나 오류 코드 문자열(`JGKB-E07/seq=41`)로 흐르는 순간 터진다.
42억 세대면 하루 한 번 백업해도 1100만 년이다.

### ⚠ `DataView(bytes.buffer)`는 `byteOffset`을 무시한다

다운로드한 봉투에서 `subarray`로 헤더를 떼면 `.buffer`가 원본 전체를 가리켜 오프셋이 전부
어긋난다. **0 오프셋 왕복 테스트로는 절대 안 잡힌다** — 회귀로 박아뒀다.

## 4. 매니페스트 — 무엇이 백업되는가

**앱의 `Diary` 타입을 쓰지 않는다.** 그건 뷰다 — 블록이 파싱돼 있고, 태그가 조인돼 있고,
묘비가 빠져 있다. 뷰를 실으면 셋이 조용히 사라진다:

1. 모르는 블록 타입 (`filter(isDiaryBlock)`이 걸러낸다)
2. 지운 조각의 묘비
3. **태그의 원래 순서** (`tags.created_at` — `ORDER BY`의 유일한 출처다)

그래서 저장소 계층을 우회하고 **원본 행**을 직접 읽는다.
→ ⚠ `db/migrations.ts`에 컬럼을 추가하면 `manifest-builder.ts`도 같이 고쳐야 한다.
   안 고치면 그 값이 백업에서 조용히 빠지고 **타입이 잡아주지 않는다.**

### 실어야 하는데 빠지기 쉬운 것

| 필드 | 왜 |
|---|---|
| `content` (파생 평문) | **파생인데도 싣는다.** `content_blocks`가 깨졌을 때의 유일한 중복성이다. 안 실으면 `parseBlocks`가 빈 배열을 주고 `content`가 `''`가 되어 **날짜만 있고 본문이 없는 조각**이 남는다(사용자에게는 사라진 것과 구별되지 않는다) |
| `dbVersion` | 봉투의 `version`은 **암호 형식**이라 스키마를 말해주지 않는다. 없으면 새 앱이 만든 백업을 옛 앱이 복원할 때 컬럼을 조용히 버리거나 raw SQL 오류로 죽는다 — 그것도 전부 받아 복호화한 뒤에. **더 새 스키마는 거부한다** |
| 묘비 | 본문은 비우되 행은 싣는다. ⚠ `content`·`created_at`·`updated_at`이 **NOT NULL**이라 "id·날짜·`deleted_at`만"으로 만들면 복원 INSERT가 통째로 실패한다 |
| `tags.created_at` | 태그 표시 순서의 유일한 출처 |

### 파트마다 완결된 JSON

큰 JSON 하나를 바이트로 잘라 나누면 읽는 쪽이 **전부 이어붙인 뒤에야** 파싱할 수 있어
힙 정점이 그대로다 — 나누는 이유(저사양 기기 OOM)가 사라진다.
파트마다 행을 나눠 담은 **독립 문서**로 만들고, 읽는 쪽은 배열을 이어붙이기만 한다.
목표 크기 **512KB**(⚠ 실기기 측정 전까지 추정치).

### UTF-8은 손으로 짰다 — 표준보다 관대하다

순수 계층은 임포트 0을 지켜야 해서 `TextEncoder`를 못 쓴다. 25개 스크립트로 Node `Buffer`와
**바이트 단위 대조**해 일치를 확인했다(§7).

⚠ **딱 한 곳이 표준과 다르고, 그게 의도다.** 짝 없는 서러게이트를 만나면
Node 표준은 `U+FFFD`로 **바꿔 원본을 파괴**하는데, 우리 인코더는 그대로 실어 왕복시킨다.

```
'앞\uD83D뒤'   내 것 : ec 95 9e  ed a0 bd  eb 92 a4   → 원본 복원 ✅
              Node : ec 95 9e  ef bf bd  eb 92 a4   → U+FFFD로 대체(손실)
```

백업은 **보존이 목적**이라 이쪽이 맞다. 다만 결과는 엄밀히는 WTF-8이므로, 서버나 외부 도구가
UTF-8 유효성을 검사하면 걸릴 수 있다 — 지금은 암호문 안에 있어 아무도 검사하지 않는다.

## 5. 서버 계약

### 3단 업로드

```
POST /api/v1/backup/reserve   → 서명 URL N개
PUT  <서명 URL>                → Storage에 **직접** (암호문이 우리 함수를 지나가지 않는다)
POST /api/v1/backup/commit    → 서버가 Storage에 실제 크기를 물어 대조
POST /api/v1/backup/latest    → 완성된 세대의 다운로드 URL
```

| 규칙 | 근거 |
|---|---|
| `seq`는 정확히 **+1**만 | 앞서면 구멍, 같거나 뒤면 덮어쓴다 |
| 같은 `seq`를 **다른 `genId`로** 다시 올리면 옛 파트를 지우고 시작 | 남겨두면 나중에 섞여 찢어진 세대가 된다 |
| `reserve`는 **멱등** — 재호출하면 URL 재발급 | ⚠ `createSignedUploadUrl` TTL이 **2시간 고정**이라 느린 업로드가 만료된다. 처음부터 다시 하게 만들면 느린 네트워크 사용자는 영원히 백업을 못 한다 |
| `commit`은 **앱이 보낸 크기를 믿지 않는다** | 앱 숫자로 쿼터를 세면 조작해 무한히 쓸 수 있다. ⚠ 서명 URL에 크기 제한 파라미터가 없어서 사후 대조가 유일한 수단이다 |
| 하나라도 없으면 **미완성으로 남기고 거부** | 반쪽 세대를 커밋하면 복원이 그만큼 조용히 잃는다 |
| `commit` 재호출은 **성공으로 답한다** | 응답 유실 재시도(멱등) |
| 객체 경로는 **서버가 조립한다** | 앱 문자열을 넣으면 `../`로 남의 금고에 쓸 수 있다 |
| `vault_id`를 **쿼리스트링에 넣지 않는다** | 액세스 로그에 남는다 — 조회지만 POST다 |

### 인가

| | |
|---|---|
| 신원 | common_server에 **introspect**(`/auth/me` + `/entitlements`, 60초 캐시). 토큰 서명을 검증하지 않는다 — 키를 공유하면 그 키가 두 곳에 생긴다 |
| ⚠ 호출이 **둘** | `/entitlements` 응답에 `subjectId`가 없다. 병렬로 부른다. ⏭ 상류에 한 줄 더하면 하나로 준다 |
| ⚠ 상류 장애는 **503이지 401이 아니다** | 앱 SDK가 401에서 `setSession(null,null)`로 **세션을 폐기한다**(`lib/common-server/index.ts:149`). common_server가 잠깐 느린 것으로 사용자가 로그아웃되면 안 된다 |
| ⚠ 상류가 죽고 **캐시가 있으면 만료돼도 쓴다** | 백업은 폰을 잃은 사람을 위한 기능인데 우리 상류가 느리다고 복원이 막히면 존재 이유가 없다 |
| 쓰기 | 구독 필요 |
| **읽기(복원)** | ⚠ **구독을 요구하지 않는다.** 폰 분실 → 결제수단이 그 폰에 묶여 갱신 실패 → 해지 → 새 폰에서 복원. 여기서 막으면 **폰을 잃은 사람을 위한 기능이 폰을 잃으면 잠긴다** |

### 소유권 — 최초 grant는 **선착순**

설계 초안에는 되찾기(rebind)만 있고 *"새 폰이 처음 이 금고를 잡는"* 경로가 없었다.
읽기에 grant가 필요한데 grant를 만드는 길이 rebind뿐이고 rebind는 복원 뒤에 오므로 **순환**이었다 —
주 시나리오(기기 분실 → 새 폰)가 계약상 불가능했다.

→ **grant가 없는 금고는 요청한 계정이 그대로 가진다.**
안전한 이유: `vault_id`가 복구 코드에서 유도되므로 남의 금고를 잡으려면 그 코드를 알아야 하고,
알면 어차피 오프라인에서 복호화할 수 있다. **새로 여는 문이 없다.**
반대로 `vault_id`만으로 인가하지는 않는다 — 그 값은 서버 DB·로그에 평문으로 있다.

`vault_grants.rebound_at` — 뺏긴 기기가 다음 접속 때 **왜 백업이 멈췄는지 알아야** 한다.

### ⚠ grant는 **읽기를 지키지 않는다** (2026-08-11 정정)

처음에는 읽기에도 grant를 요구했다. 그러면 **순환**이 남는다 —
읽기에 grant가 필요하고 grant를 옮기는 되찾기는 복원 뒤에 오는데, 복원이 곧 읽기다.
"최초 grant는 선착순"이 주 시나리오를 뚫어줬을 뿐, 남이 grant를 쥔 경우는 여전히 막혀 있었다.

**읽기를 연다(Bearer만).** 근거는 간단하다 — **읽기는 암호가 이미 지킨다.**
`vault_id`를 아는 사람이 얻는 것은 **못 여는 암호문**이고, 열려면 복구 코드가 필요하며,
코드가 있으면 어차피 오프라인에서 열 수 있다. grant가 존재하는 이유는 **단일 라이터**를
강제하는 것이지 열람을 막는 것이 아니다.

| 동작 | 인가 |
|---|---|
| `latest` · 다운로드 | **Bearer만** |
| `reserve` · `commit` | Bearer + grant (없으면 **선착순으로 잡는다**) |
| `rebind` | Bearer + **`auth_key`** (아래) |
| `delete` | Bearer + (grant **또는** `auth_key`) |

### 되찾기 인가 — `auth_key`를 **해시로** 보관한다

`rebind`를 Bearer만으로 열면 `vault_id`를 아는 사람이 라이터를 뺏을 수 있다.
읽지는 못하지만 **주인의 백업을 멈추고 쓰레기 세대를 올릴 수 있다** — 실질적 피해다.

```
auth_key = HKDF-SHA256(복구 코드, "jogak/auth/v1", 32B)
서버 저장 = sha256(auth_key)          ← 원본은 저장하지 않는다
```

- 금고를 처음 만들 때(첫 `reserve`) 앱이 `auth_key`를 보내고 서버는 **해시만** 남긴다.
- 되찾기·삭제는 `auth_key`를 제시한다. 서버는 해시를 대조한다.
- **서버 DB가 통째로 새도 되찾기 권한은 안 샌다** — 해시는 되돌릴 수 없다.

⚠ 대칭 비밀이라 요청 중에는 평문으로 전송·메모리 상주한다. TLS 밖으로 나가지 않고
**절대 로그에 남기지 않는다**(`lib/observability.ts` 규율). 비대칭(Ed25519)이면 이 잔여
노출도 없지만 `@noble/curves`라는 세 번째 의존성과 챌린지 엔드포인트·nonce 테이블·리퍼가
따라온다 — **해시 보관만으로 "DB 유출 ≠ 권한 유출"이라는 핵심 이득은 이미 얻는다.**
⏭ 다시 열 조건: 되찾기 남용이 실제로 보고되거나, 서버가 이미 비대칭을 쓰게 될 때.

### 리퍼 — 실패한 업로드를 치운다

| 대상 | 기준 | 왜 |
|---|---|---|
| `reserved`인 채 남은 파트 | **24시간** | 서명 URL TTL이 2시간이라 그 뒤엔 못 올린다. 그래도 24시간을 두는 건 **느린 재시도를 죽이지 않기 위해서**다 — `reserve`는 멱등이라 재발급받아 이어갈 수 있다 |
| 미완성 세대 | 파트가 전부 사라지면 함께 | 커밋되지 않은 세대는 복원 대상이 아니다 |
| 보관 세대 수 | **최근 3개** | 잘못된 복원을 되돌릴 여지. ⚠ **복원 출처 세대는 다음 성공 백업 2회까지 evict 금지** — 되돌리려는데 그게 지워져 있으면 안 된다 |

### 파기 — 유예 90일, 툼스톤 1년

구독이 끊기면 **90일 유예 후 파기**한다(`CLAUDE.md` §7.2 확정). 텍스트도 사진도 같다 —
텍스트 저장 단가는 거의 0이지만, **복원이 영구 무료면 구독을 끊어도 핵심 가치가 남아
구독 이유가 하나 줄어든다.** 저장 비용보다 그쪽이 크다(2026-08-11 사용자 결정).

파기는 객체를 지우고 `vaults.purged_at`을 찍는다 — 행은 남긴다(툼스톤). 툼스톤은 **1년 뒤** 삭제.

### 🔴 통지 — "반드시 알린다"를 지킬 수 없다. 약속을 고친다

`CLAUDE.md` §7.2가 *"유예 만료 전 **반드시** 알린다. 조용히 지우면 그게 최악이다"* 라고
적어뒀는데 **채널이 없다** — 푸시 미구현, 원격 관측 0, 이메일 발송 경로 0.
남는 건 앱 내 배너뿐인데 **폰을 잃은 사람은 앱을 안 연다.**

지킬 수 없는 약속을 두면 그게 가장 비싸다. **약속을 우리가 할 수 있는 것으로 바꾼다:**

| 하는 것 | 언제 |
|---|---|
| **백업을 켜는 화면에서 미리 말한다** — *"구독이 끝나면 90일 뒤 백업이 삭제돼요"* | 켜기 전 (PD&C 고지에 포함) |
| **앱을 열면 배너로 알린다** — 남은 일수와 삭제 예정일 | 구독 만료 후 매 실행 |
| **백업 화면에 삭제 예정일을 상시 표시** | 유예 중 |
| **못 하는 것을 그 자리에 적는다** — *"앱을 열지 않으시면 이 안내가 닿지 않아요"* | 위 고지와 같은 화면 |

⚠ `CLAUDE.md` §7.2의 *"반드시 알린다"* 를 **취소선으로 정정**했다. 지킬 수 없는 절대 약속을
문서에 남겨두면 다음 사람이 그걸 근거로 설계한다.

⏭ 푸시가 붙으면(지금은 화면만 있고 발송이 없다) 이 표의 첫 줄이 진짜 통지가 된다.
   그때 §7.2를 다시 강하게 쓸 수 있다.

#### 배너를 어떻게 다루나 (2026-08-11 결정)

| | |
|---|---|
| 어디에 | **홈 최상단.** 백업 화면에만 두면 안 본다 — 백업 화면에 들어가는 사람은 이미 아는 사람이다 |
| 닫을 수 있나 | **없다.** 일기가 지워지기까지의 카운트다운이고, 한 번 닫으면 다시 볼 이유가 사라진다. 기둥 2("화면이 조용해야")를 여기서만 굽힌다 — 되돌릴 수 없는 손실이 걸려 있다 |
| 파기 뒤에는 | **홈에서 사라진다.** 막을 손실이 이미 일어났고, 영구히 남는 알림은 잔소리다. 사실은 백업 화면에 남는다 |
| 누르면 | 백업 화면 — 거기서 삭제 예정일과 다시 구독하는 길을 본다 |

⚠ **유예 시계는 앱이 스스로 센다**(`purgeAtFrom(proUntil)`). 서버에 물어보지 않는다 —
   이 배너는 **오프라인에서도 떠야** 하고, 유예 중인 사람은 정의상 결제가 끊긴 사람이라
   네트워크 상태를 신뢰할 근거가 없다. 값의 출처는 마지막으로 서버가 준 `pro_expires_at`이다.

⚠ **유예 시계의 출처는 `pro_expires_at` 스냅샷이다.** 만료는 이벤트로 오지 않는다 —
   common_server는 `active`를 저장하지 않고 **읽을 때 계산**하므로 만료 순간에 DB를 쓰는
   주체가 없다. 조각 서버가 introspect로 받은 만료 시각을 저장해두고 자기 쪽에서 센다.

### 탈퇴 → 백업 파기 — 아웃박스를 **쓸 수 없다**

정답은 common_server에 `subject_events` 아웃박스를 두고 조각 서버가 소비하는 것이다.
그런데 **`common_server`는 수정 금지**라 그 길이 막혀 있다.

**그래서 앱이 탈퇴 직전에 지운다.**

```
탈퇴 버튼 → DELETE /api/v1/backup (조각 서버)  → 실패하면 **탈퇴를 진행하지 않는다**
          → commonServer.deleteAccount()
```

⚠ **새 실패 모드가 아니다.** `deleteAccount()` 자체가 네트워크 작업이라 오프라인이면
어차피 탈퇴가 안 된다. 순서만 하나 늘어난다.

남는 구멍과 대응:

| 구멍 | 대응 |
|---|---|
| 탈퇴 없이 **앱만 지운 경우** | 계정 삭제가 아니라 방치다. 파기 의무는 없지만 무한 누적은 막아야 하니 **3년 무접근 금고를 리퍼가 정리**하고 처리방침에 명시한다 |
| 삭제는 성공했는데 `deleteAccount()`가 실패 | 백업만 사라지고 계정은 남는다. 사용자에게는 손해지만 **되돌릴 수 없는 쪽(계정)이 보존**되므로 이 순서가 맞다 |

⏭ `common_server`를 손댈 수 있게 되면 아웃박스로 바꾼다 — 그게 정답이다.
   그때까지 이 한계를 **Play 데이터 보안 선언·처리방침 문구가 감당할 수 있는 범위**로 적는다:
   "앱에서 탈퇴하시면 백업도 함께 삭제됩니다"는 참이다.

### 파기는 행을 남긴다 (툼스톤)

`vaults.purged_at`. 행을 지우면 404밖에 못 주고, **404를 받은 사용자는 자기 일기가 지워졌다는
사실을 영원히 모른다** — "서버가 이상한가 보다"로 읽는다. 410을 주려면 행이 필요하다.
⚠ 툼스톤에 `subject_id`를 남기지 않는다("탈퇴 시 지체 없이 파기"와 충돌).

## 5.5 사진 백업 (2차)

텍스트(매니페스트)와 **완전히 다른 물건**이다. 매니페스트는 세대마다 통째로 다시 올리지만,
사진은 **한 번 올리면 끝**이고 세대와 무관하게 산다 — 조각 500개짜리 사용자가 오늘 한 줄
고쳤다고 사진 300장을 다시 올릴 수는 없다.

```
매니페스트  세대마다 전량      seq에 묶인다        512KB × N 파트
사진 blob   이미지당 한 번     seq와 무관하다      장당 ~300KB, 상한 2GB
```

### ① blob 키 — **콘텐츠 주소가 아니다**

초안은 `sha256(암호문)`이었는데 **성립하지 않는다.** nonce가 매번 랜덤이라 같은 사진도
암호문이 달라지고, 그러면 재시도할 때마다 새 경로가 생겨 **중복 업로드가 쌓인다.**

`sha256(평문)`도 안 된다 — 서버가 "이 사용자가 이 사진을 갖고 있는가"를 **확인할 수 있게 된다**
(알려진 이미지의 해시와 대조). 일기 앱에서 그건 작지 않은 누출이다.

→ **키를 유도한다.**

```
blob_key = HKDF-SHA256(DEK, "jogak/blob/v1" ‖ image_id, 32B)  → 소문자 hex 64자
경로     = {vault_id}/blobs/{blob_key}
```

- 이미지 하나 = blob 하나. **재업로드가 같은 경로를 덮는다**(멱등).
- 서버는 키에서 아무것도 알 수 없다(HKDF 단방향).
- 중복 제거는 **하지 않는다.** 같은 사진을 두 조각에 넣으면 `image_id`가 다르므로 두 벌
  올라간다 — 축소된 사진이 장당 ~300KB라 이 낭비가 개인정보 위험보다 싸다.

⚠ 봉투 `type=1`의 context를 ~~`sha256(암호문)`~~ → **`blob_key` 32B**로 바꾼다.
   그래야 봉투가 **자기가 놓일 자리에 묶인다** — 다른 경로에 올려두면 AEAD가 걸러낸다.

### ② `blob_state` — 세 상태

| 값 | 뜻 | 화면 |
|---|---|---|
| `NULL` | 로컬 파일만 있다. 아직 안 올렸다 | 정상 표시 |
| `'backed_up'` | 로컬에도 있고 서버에도 있다 | 정상 표시 |
| `'missing'` | **행은 있는데 로컬 파일이 없다** | *"이 사진은 이 기기에 없어요"* |

⚠ `'missing'`과 "잠시 로딩 실패"를 **구분해야 한다.** 지금 화면은 둘 다
*"이미지를 불러오지 못했어요"* 로 보여준다 — 사용자는 그걸 일시적 오류로 읽고
**원본을 지운다.** 문구를 갈라야 한다.

### ③ 올리는 순서 — **blob 먼저, 매니페스트 나중**

반대로 하면 커밋된 세대가 **없는 사진을 가리킨다.** 복원한 사람은 행은 받았는데 파일이
영원히 안 오는 상태가 되고, 그건 화면에서 "손상"과 구별되지 않는다.

```
1. blob_state ≠ 'backed_up' 인 이미지만 골라 올린다   ← 증분의 전부
2. 매니페스트를 올린다(3단)
3. commit 성공 후에야 blob_state = 'backed_up'
```

⚠ **3번을 2번 앞에 두면 안 된다.** 커밋 전에 표시해두면, 커밋이 실패했을 때 다음 백업이
그 사진들을 "이미 올렸다"고 건너뛴다 — 서버에는 없는데 앱은 있다고 믿는다.

### ④ GC — **서버는 무엇이 참조되는지 모른다**

매니페스트가 암호문이라 서버는 그 안의 이미지 목록을 읽을 수 없다. 그래서 blob이 고아인지
서버 혼자서는 판정할 수 없다.

→ **앱이 백업할 때마다 참조 목록을 보낸다.** 그게 `plan`이다 — 앱은 "이 사진들이 지금
  살아 있다"를 묻고, 서버는 그 자리에서 `referenced_at`을 갱신한다. 내용이 아니라
  **"이 금고가 이 blob들을 가리킨다"** 는 메타데이터다(`vault_id`·개수·크기는 이미 평문이다).

⚠ **세대별 참조표(`generation_blobs`)를 만들지 않았다.** 사진은 세대와 무관하게 살고
   (한 번 올리면 끝), 세대마다 참조를 복사하면 세대 보관 개수(3)와 사진 수명이 얽혀
   *"옛 세대를 지웠더니 현재 사진이 사라지는"* 경로가 생긴다. **금고 단위 `referenced_at`
   하나**로 충분하고, 그게 실제로 지키려는 것("최근 백업이 가리킨 적 있는가")과 정확히 같다.

⚠ **유예를 둔다.** "현재 매니페스트에 없으면 즉시 삭제"로 만들지 않는다 —
   실패한 백업이 참조 목록을 못 보낸 사이에 멀쩡한 blob이 지워진다.
   **7일**(`BLOB_ORPHAN_MS`)을 준다.

### ⑥ 금고는 **사진도 만들 수 있다** (2026-08-11 정정)

~~금고는 매니페스트 예약만 만든다~~ → **쓰기 갈래(`plan`·`reserve`·`commit`)가 모두 만든다.**

사진이 매니페스트보다 **먼저** 가야 하는데(③) 금고 생성이 매니페스트 전용이면
**첫 백업이 `no-vault`로 영원히 막힌다.** 실제로 막혔다 — 순서 결정과 생성 권한이
어긋나 있었고, 서버 e2e가 금고를 미리 만들어 두는 바람에 계약 검사도 이걸 놓쳤다.
지금 e2e는 **금고를 미리 만들지 않는다.**

⚠ 그래서 **쓰기 갈래는 `auth_key`를 함께 보낸다.** 사진이 금고를 키 없이 먼저 만들면
  되찾기·코드로 삭제가 **영영 막힌 금고**가 남는다. `ensureVault()`는 비어 있는 해시를
  채우되 **이미 있는 해시는 덮지 않는다** — 빈 칸 채우기와 덮어쓰기는 다르다.
  `download`는 금고를 만들지 않는다(읽기가 껍데기를 만들면 리퍼가 치울 것만 는다).

### ⑤ 🔴 로컬 고아 파일 정리는 **아직 하지 않는다**

`DIARY_SYSTEM.md` §1.2가 *"실제 파일 정리 시점은 백업 착수 시 정한다(지금 지우면 복원할
방법이 없다)"* 로 미뤄둔 항목이다. 사진 백업이 붙었으니 이제 정할 수 있지만, **아직 켜지 않는다.**

이유: 1차 복원이 **고아를 대량 생산한다.** 사진이 있는 기기에서 복원하면 `diary_images` 행이
교체되어 옛 파일들이 아무 행에도 참조되지 않는다. 그 순간 GC를 돌리면 **백업본이 없는 사진이
전부 영구 삭제**된다.

**켤 수 있는 조건과 규칙:**
- 사진 백업이 실제 사용자 데이터로 검증된 뒤에만 켠다
- 지울 수 있는 것은 **`blob_state = 'backed_up'` 인 행이 참조하던 파일뿐**이다
  (= 서버에 사본이 있다)
- 참조가 없는데 서버에도 없는 파일은 **절대 지우지 않는다.** 용량을 잃는 것이 일기를
  잃는 것보다 낫다

## 6. 복원 = 전체 교체

병합하지 않는다. 주 시나리오(새 폰)에서는 로컬이 비어 있어 교체가 곧 정답이고, 병합 하나를
들이면 `rev`·`origin`·충돌 화면·15개 언어 문구·"백업 차단" 상태기계가 전부 따라온다.

### 그 대가 — 확인 화면이 선택이 아니라 조건이다

⚠ **진짜 다수 케이스는 "두 기기 병행 작성"이 아니라 "로컬이 비어 있지 않은데 복원"** 이다.
백업이 수동 버튼인 한 스테일은 기본값이고, 3주 전 백업 + 그 뒤 20개 작성 상태에서 복원을
누르면 20개가 사라진다.

- **차집합 D = 로컬 alive id ∖ 매니페스트 alive id**를 세고 **날짜까지** 보여준다.
  "497개가 대체됩니다"는 위험을 표현하지 못한다 — 사라지는 건 20개다.
- 🔴 **매니페스트 쪽은 반드시 alive만.** 묘비 id를 포함하면 "A 기기에서 지운 조각"이 B 기기에서
  "백업에 있음"으로 판정돼 **경고 없이 사라진다** — 이 화면이 막으려던 바로 그 손실이다.

### 테이블 분류

| 분류 | 대상 |
|---|---|
| **교체** | `diaries` · `diary_images` · `tags` · `diary_tags` |
| **보존** | `app_settings` 전체 + `backup_state` |
| **병합** | **없음** |
| **외부(건드리지 않음)** | `Paths.document/diary-images/` 파일 트리 |

- ⚠ `app_settings`를 건드리면 **언어가 날아가** 복원 직후 안내를 **못 읽는 언어로** 만난다.
- ⚠ `backup_state`가 교체 대상 안에 있으면 두 갈래로 깨진다 — 지워지면 `seq=1`을 올려 충돌하고,
  남으면 **복원 전 기기의 커서**라 역시 어긋난다. 그래서 별도 테이블이다.
- ⚠ `blob_state`를 매니페스트 값이 아니라 **`'missing'`으로 강제**한다. 1차는 사진 파일을
  안 가져오므로 원본의 `'present'`를 쓰면 "파일이 있다"고 주장하는 행이 생긴다.
- 복원의 **마지막 단계**가 커서를 복원한 세대로 맞춘다. 빠뜨리면 직후 첫 백업이 409를 받는다.

### 🔴 되찾기가 막다른 길이었다 (2026-08-11 발견)

`no-grant`일 때 앱은 *"다른 기기가 이 백업을 쓰고 있어요. 여기서 복원하면 가져올 수 있어요"*
라고 안내한다. 그런데 **복원 경로 어디에도 `rebind` 호출이 없었다.** `takeOverWriter()`는
만들어져 있었지만 **어느 화면에도 연결되지 않았다.**

결과: 안내대로 복원해도 다음 백업이 다시 `no-grant`로 막힌다. 사용자가 할 수 있는 일이
없고, 화면은 계속 "복원하세요"라고 말한다. 3판이 *"409를 받은 클라이언트의 선택지가
덮어쓰기(계약 금지)와 영구 포기 둘뿐"* 이라고 지적한 그 상태가 실제로 남아 있었다.

**고친 방식**: 복원이 성공한 뒤 **`takeOverWriter()`를 부른다.** 순서가 중요하다 —
먼저 되찾으면 상대 기기의 백업을 멈춰놓고 이쪽 복원이 실패할 수 있다.
복원이 끝난 기기는 서버 내용과 같으므로, 그때 라이터를 가져오는 것이 정의상 안전하다.

⚠ 되찾기 실패는 **복원 실패로 올리지 않는다.** 조각은 이미 들어왔다 — 다음 백업에서
  다시 시도하면 된다. 여기서 실패로 뒤집으면 성공한 복원을 되돌리게 된다.

### 🔴 introspect가 태평양을 왕복한다 (측정, 2026-08-11)

| 경로 | 시간(개발 머신 기준) |
|---|---|
| `/api/health` (introspect 없음) | **0.10초** |

태평양을 왕복하면 매 요청 수백 ms다 — 착수 전에 실측한다"* 로 남겨둔 항목의 답이다.

- **원인은 common_server의 `vercel.json`에 `regions` 키가 없다는 것**이다(크론만 있다).
  조각이 고칠 수 없다 — common_server 쪽 작업이다.

  my_word·배구명가의 모든 요청에도 같은 이득이 있다.

⚠ **`AUTH_STUB=1`은 로컬 전용이다.** 지금 구조는 *로컬 Next → 클라우드 Supabase*라 서버가

**테스터의 시험 데이터가 운영에 남는다** — 신규로 만들고 stg는 버리는 쪽이 깨끗하다.

```

cp .env.example .env.local  # supabase status 의 SERVICE_ROLE_KEY 붙여넣기
```

- ⚠ 기본 포트(5432x)를 **다른 프로젝트의 Supabase 스택이 쓰고 있어** 544xx로 옮겼다.

1. **번들 종류가 원인이 아니다.** dev와 `--no-dev --minify`가 거의 같다(1.34 vs 1.20) —
   Hermes lazy 컴파일 탓이라면 큰 차이가 났어야 한다. **에뮬레이터가 느린 것**이다.
   x86_64 에뮬레이터의 JS 실행은 실기기 ARM보다 통상 2~4배 느리다. ⚠ 실기기 재측정이 남았다.
2. **실사용 시간이 문제가 안 된다.** 512KB 파트가 **0.42초**다. 조각 1000개(≈2.4MB)면
   전체 봉인이 **2초**다. 수동 버튼 + 진행률이라 이 정도는 보이지도 않는다.
3. **libsodium의 대가가 크다.** 네이티브 모듈이라 `check:backup-crypto`(43개 검사)가
   **통째로 못 돌게 된다** — Node에서 임포트가 안 된다. KAT를 잃는 대가로 얻는 것이
   "2초 → 0.5초"라면 남는 장사가 아니다.
4. 진짜 병목은 암호가 아니라 **업로드**다. 5MB PUT이 **70초**였다(같은 에뮬레이터).

→ **순수 JS 유지. 파트 크기 512KB 유지.**
   ⏭ 실기기에서 다시 재고, 그때도 1.5 미만이면서 사용자가 체감하면 그때 다시 연다.

측정 도구는 `features/backup/api/device-check.ts`. `EXPO_PUBLIC_DEVICE_CHECK=1`로 켜고
`adb logcat -s ReactNativeJS | grep jogak-check`로 읽는다.
⚠ **`__DEV__`로 게이트하면 릴리스에서 잴 수 없다** — 그래서 환경변수다. 기본값은 꺼짐.

### 🔴 복원을 스크래치 스왑으로 바꾼다 (측정 결과에 따른 설계 변경)

`backupDatabaseAsync`가 **열린 커넥션을 목적지로 받는다**는 것이 확인됐다(9ms, WAL 유지).
지금은 라이브 DB에 직접 써서 **복원 중 앱이 죽으면 반쯤 교체된 상태가 남는다.**

```
1. 스크래치 DB를 새로 열고 migrate()                    ← 라이브에 락 0
2. 복호화·파싱·검증·청크 INSERT를 전부 스크래치에        ← 이 동안 앱은 완전히 정상
3. 검증 (user_version · COUNT · integrity_check)
4. 보존 대상(app_settings·backup_state)을 라이브 → 스크래치로 복사
5. 센티넬 기록 → backupDatabaseAsync(라이브 → pre-restore.db) → 검증
6. backupDatabaseAsync(스크래치 → 라이브) **한 번**       ← 유일한 락 구간, 9ms
7. 센티넬 제거 → 스토어 refresh + treeKey 리마운트
```

**반쯤 교체된 라이브 DB가 원리적으로 존재하지 않는다.** 6번 이전 어디서 죽어도 라이브는
무손상이고, 되돌리기가 필요한 창이 30초에서 **9ms**로 줄어든다.

⚠ 4번이 빠지면 **테마·언어·백업 커서가 날아간다** — 스크래치는 `migrate()`로 만든 빈
`app_settings`를 갖고 있다. "보존"은 분류가 아니라 **명시적 복사 동작**이어야 한다.
스왑에는 테이블 단위 개념이 없기 때문이다.

✅ **구현·검증 완료**(2026-08-11). 에뮬레이터에서 실제 데이터로 왕복했다:

| 검사 | 결과 |
|---|---|
| 스크래치 스왑 복원 | **314ms** · 조각 6/6 |
| 복원 후 다국어 본문 일치 | **5/5** (한국어·日本語·中文·ไทย·ZWJ 이모지) |
| 태그 연결·묘비 보존 | 둘 다 |

### 중단 복구 게이트는 `getDatabase()` 안에 있다

⚠ **`app/_layout.tsx`에 두면 늦다.** `ThemeProvider`가 `LockGate` **바깥**에서
`getSetting`으로 DB를 열고, 언어·공지·광고가 `void`로 게이트를 앞지른다.
`getDatabase()`가 **모든 DB 접근이 반드시 지나는 유일한 지점**이다.

센티넬(`restore-pending.json`)은 **DB 밖 파일**이고 **불리언이 아니라 3상태**다:

| phase | 게이트가 하는 일 | 왜 |
|---|---|---|
| `preparing` | 마커만 지운다 | 라이브를 건드린 적이 없다 |
| `snapshotted` | 스냅샷으로 되돌린다 | 스왑 도중 죽었을 수 있다 |
| `swapped` | **커서만 마무리한다** | 되돌리면 **성공한 복원을 날린다** |

⚠ 마커는 **스냅샷 검증 뒤에** 올린다. 순서를 뒤집으면 "마커는 있는데 스냅샷은 비어 있는"
구간이 생기고, 게이트가 **멀쩡한 라이브를 빈 DB로 되돌린다** — 빈 DB도 `integrity_check`는
통과하므로 그걸로는 못 거른다.

### 🔴 기기에서만 드러난 것 3개 (2026-08-11)

셋 다 **서버 e2e 32개를 전부 통과한 채로** 죽어 있었다. 계약 검사가 Node에서 도는 한
이 종류는 절대 잡히지 않는다 — 그래서 기기 점검을 지운 적이 없다.

| 증상 | 진짜 원인 | 고친 것 |
|---|---|---|
| 모든 서버 호출이 **"오프라인"** | **Hermes에 `AbortSignal.timeout()`이 없다.** `catch`가 그걸 오프라인으로 번역했다 — 네트워크는 멀쩡했다 | `fetchWithTimeout()`(AbortController + `finally` 타이머 해제) |
| 첫 백업이 **`no-vault`** | 사진이 먼저 가는데 금고는 매니페스트만 만들었다 | §5.5 ⑥ |
| 서명 URL PUT이 **`Network request failed`** | 서명 URL의 호스트가 `127.0.0.1` — **에뮬레이터에게는 자기 자신**이다 | `SUPABASE_PUBLIC_URL`로 출처만 갈아끼운다(운영에서는 같은 값이라 무동작) |

⚠ **`AbortSignal.timeout`을 다시 쓰지 않는다.** 타입 정의에는 있어서 `typecheck`가 통과하고,
   Node에서 도는 e2e도 통과한다. 기기에서만 던진다.

⚠ 그리고 **부수효과를 `onProgress?.(...)` 인자 안에 두지 않는다.** 옵셔널 체이닝은 호출을
   통째로 건너뛰므로 콜백이 없으면 `++`가 실행되지 않는다 — 복원이 실제로 됐는데
   "0장 복원"으로 보고했다.
