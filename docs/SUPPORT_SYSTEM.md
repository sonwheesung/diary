# 조각 — 공지 · 문의 (common_server 연동)

> 서버 경계와 이유는 [`ARCHITECTURE.md`](./ARCHITECTURE.md) §2·§4, 정책은 [`../CLAUDE.md`](../CLAUDE.md) §4·§5.
> 이 문서는 **조각 앱 쪽 구현**이 정본이다. 서버 계약의 정본은 `common_server/docs/PLAN.md` §5.
> 2026-08-09 구현.

---

## 1. 한 줄 요약

공지와 문의는 **common_server**가 맡는다. 조각은 SDK를 **복사해 와서** 쓰고, 서버가 죽어도
일기 기능은 그대로 돌아간다.

---

## 2. 구성

| 파일 | 역할 |
|---|---|
| `lib/common-server/index.ts` · `types.ts` | **common_server/client/에서 복사한 SDK. 손대지 않는다** |
| `lib/common-server/client.ts` | 조각 전용 인스턴스 — `appCode`·`baseUrl`·`platform` 주입 |
| `features/notice/store.ts` | 부팅 조회(zustand) · 읽음 관리 |
| `features/support/auth-gate.ts` | ⏭ 문의 로그인 게이트 **임시 자리** |
| `app/notice.tsx` · `app/support.tsx` | 화면 |
| `.env` (커밋 안 함) · `.env.example` | `EXPO_PUBLIC_SERVER_URL` |

### SDK를 복사하는 이유

common_server 규약이다 — 앱 4~5개 규모에서 monorepo·npm 패키지 오버헤드가 이득보다 크다.
**복사본에는 원본 경로와 복사 시점을 주석으로 남긴다.** 서버 계약이 바뀌면 원본을 갱신하고
다시 복사한다. 복사본을 손으로 고치면 다음 복사 때 조용히 되돌아간다 —
그래서 `eslint.config.js`에서 이 두 파일만 우리 린트 규칙을 면제한다.

## 3. 부팅 조회 (`GET /api/v1/bootstrap`)

앱 실행당 **1회**. 점검·버전·공지를 한 번에 받는다. `app/_layout.tsx`에서 부른다.

```
{ maintenance, version: { min, latest, androidUrl, iosUrl }, announcements: [...] }
```

### ⚠ 점검·버전 게이트를 쓰지 않는다 (조각의 결정)

응답에 `maintenance`와 `version`이 오지만 **조각은 둘 다 무시한다.**

일기는 기기에 있고 서버 없이 완전히 동작한다(기둥 3). 서버 점검을 이유로 사용자를 자기 일기에서
잠그는 것은 정당화되지 않는다 — 서버가 못 하는 일이 하나도 없는 화면까지 막게 된다.
버전 게이트도 같은 이유로 두지 않는다.

> my_word는 점검 게이트를 쓴다. 그쪽은 서버 없이는 성립하지 않는 기능이 있어서고,
> 조각과 판단이 갈리는 지점이다. 베껴오지 않는다.

### 실패는 조용히

`boot`은 null로 남고 공지 목록은 **빈 상태**로 보인다. 에러 화면을 띄우지 않는다 —
사용자가 할 수 있는 일이 없는 실패를 굳이 알릴 이유가 없다.

## 4. 공지 읽음 — 로컬 전용

읽은 공지 id는 `app_settings.notice_read_ids`(JSON 배열)에 쌓는다.
**서버에 읽음을 보내지 않는다** — 익명 접수라 서버가 "누가 읽었는지" 알 방법이 없고,
알 수 있게 만들면 익명성이 깨진다.

- 저장할 때 **서버가 내려준 id와 교집합만** 남긴다. 안 그러면 만료·삭제된 공지의 id가 영원히 쌓인다.
  공지 id는 서버에서 재사용하지 않으므로 지워도 안전하다.
- 공지 화면에 들어오면 전부 읽음으로 기록하되, **화면에 뜬 새 글 표시는 그대로 둔다**(입장 시점 스냅샷).
  들어오자마자 표시가 사라지면 무엇이 새 글이었는지 알 수 없다.
- 설정의 배지는 **개수를 쓰지 않는다.** 몇 개인지보다 "새 게 있다"가 필요한 정보다.

## 5. 문의 (`POST /api/v1/tickets`)

| 보내는 것 | 안 보내는 것 |
|---|---|
| 분류(bug·suggestion·question·etc) · 본문 · 플랫폼 · 앱 버전 · **로그인 이메일·구글 sub**(귀속) | **일기 본문 · 기기 식별자** |

⚠ **정정(2026-08-11)**: ~~안 보내는 것에 "계정"~~ — 로그인이 붙은 뒤로 거짓이다.
`tickets.subject_id`로 귀속되므로 계정은 **보내는 쪽**이다.

화면 문구도 같은 이유로 고쳤다. ~~*"일기 내용은 보내지 않아요. 앱 버전과 기기 종류만 함께 전달돼요."*~~
→ **`support.privacyNote`**: *"문의 내용, 로그인에 쓴 이메일 주소, 앱 버전, 기기 종류가 함께
전달돼요. 일기 내용은 보내지 않아요."*

**부인을 뒤로 뺐다.** 앞에 두면 수집 고지가 각주처럼 읽힌다 — 옛 문구의 결함이 정확히 그거였다.
일기 앱에서 "일기는 안 간다"가 가장 중요한 한 줄인 건 그대로지만, 그 앞에 **무엇이 가는지**가 와야 한다.

🔴 **수집이 실제로 시작되는 곳은 이 화면이 아니라 로그인 게이트다.** 거기엔 고지가 한 줄도
없었고 처리방침 링크도 없었다(처리방침은 설정 탭에서만 닿았다). `support.loginPrivacyNote` +
처리방침 링크를 **로그인 버튼 위에** 넣었다 — 개인정보위 작성지침(2025.4)이 모바일 앱의
'가입·로그인' 화면에도 처리방침을 두도록 개선한 자리다.

- 본문 하한 5자 / 상한 2000자 — **서버 상수와 같은 값**을 SDK가 export한다(`CONTENT_MIN`/`CONTENT_MAX`).
  입력창 `maxLength`를 상한보다 크게 두면 잘린 글을 보낸 줄 모른다.
- 실패 사유별로 다른 문구를 띄우되, `not-found`(앱 미등록)는 `not-configured`와 **같은 문구**로 묶는다.
  우리 쪽 사정을 설명해봐야 사용자가 할 수 있는 일이 없다.

### 로그인 (2026-08-09 서버·SDK 준비 완료)

문의는 로그인 필수다(CLAUDE.md §4) — **답변을 드리려면 누가 보냈는지 알아야** 하기 때문이다.
서버가 이제 그걸 받는다: `tickets.subject_id`로 귀속되고 `fetchMyInquiries()`로 답변을 읽는다.

| 서버·SDK | 상태 |
|---|---|
| `POST /api/v1/auth/login` (구글 토큰 검증) | ✅ |
| `GET`·`DELETE /api/v1/auth/me` (세션 확인·탈퇴) | ✅ |
| `GET /api/v1/tickets/mine` (내 문의·답변) | ✅ |
| SDK `login` · `restoreSession` · `logout` · `deleteAccount` · `fetchMyInquiries` | ✅ |

세션 판정은 `features/support/auth-gate.ts`가 전부 갖고, 화면은 `signedIn`만 보고 갈라진다.

**세션 토큰은 SecureStore에 둔다**(`lib/common-server/client.ts`). 토큰을 쥔 사람이 곧 그 계정이라
PIN 해시·암호화 키와 같은 급의 자격증명이다 — `app_settings`(평문 SQLite)에 두지 않는다(§7.1).

⚠ **오프라인에서 로그아웃시키지 않는다.** 세션 폐기는 서버가 401로 명시적으로 거절했을 때만이다.
지하철에서 앱을 켰다고 로그아웃되면 안 된다. 오프라인이면 "기기에 토큰이 있는지"로 판단한다.

#### 구글 로그인 (2026-08-09 구현)

`features/support/auth-gate.ts`가 `@react-native-google-signin/google-signin@16.1.4`를 부른다.

| 것 | 어디 |
|---|---|
| `configure({ webClientId })` | **모듈 로드 시 1회.** 훅 안에서 부르면 화면을 열 때마다 다시 불린다 |
| `signIn()` | `hasPlayServices()` → `GoogleSignin.signIn()` → `idToken` → `commonServer.login('google', …)` |
| `signOut()` · `deleteAccount()` | 구글 세션과 우리 세션을 **둘 다** 정리한다 |
| 화면 | `app/support.tsx` — 로그인 버튼 · 계정 줄(로그아웃 · 탈퇴) |

지키는 것:

- **취소는 오류가 아니다.** `signIn()`은 `'cancelled'`를 돌려주고 화면은 아무 말도 하지 않는다.
  창을 닫자마자 오류창이 뜨면 실패한 것처럼 보인다.
- **`idToken`이 `null`이면 `'not-configured'`로 돌린다.** `webClientId`가 없거나 틀리면 로그인
  자체는 성공하는데 토큰만 비어 온다 — 그대로 서버에 보내면 설정 문제가 `unauthorized`(인증 문제)로 보인다.
- **서버가 거절하면 구글 세션도 끊는다.** 남겨두면 다음 시도에서 계정 선택 창이 안 뜨고 같은 계정으로
  조용히 재시도되어, 계정을 바꿔볼 길이 없어진다.
- **탈퇴는 `revokeAccess()`까지 한다.** `signOut()`만 하면 다음 로그인에서 동의 화면 없이 같은 계정으로
  되돌아가, 방금 탈퇴한 사람에게 "지워지긴 한 건가" 싶어진다.
- **`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`가 비면 `configure()`를 아예 부르지 않는다.** 빈 값으로
  설정해두면 SDK 내부에서 죽어 `'not-configured'`와 구분되지 않는 오류가 난다.

⚠ **서버가 `jogak`을 등록하기 전에는 로그인이 성공할 수 없다**(§6). 앱 쪽은 끝났고 서버 쪽이 남았다.

#### OAuth 동의 화면은 '테스트 중'이면 등록된 계정만 로그인된다 (2026-08-09에 걸림)

Google Cloud → 인증 플랫폼 → **대상**의 게시 상태가 `테스트 중`이면, **테스트 사용자 목록에 있는
계정만** 로그인할 수 있다. 앱이 아니라 **구글이** 막으므로 우리 서버 로그에는 아무것도 남지 않는다.

2026-08-09에 `프로덕션 단계`로 올렸다. 조각은 `email`·`profile`·`openid`(비민감 범위)만 쓰므로
**구글 검증 심사가 필요 없다** — 심사는 민감/제한 범위, 로고 등록, 도메인 10개 초과일 때만이다.

⚠ 이 프로젝트(`google-oauth-test`)에는 **배구명가 클라이언트도 함께 있다.** 동의 화면은
프로젝트 단위라 이 변경은 배구명가에도 적용된다(막던 것이 풀리는 방향이라 해를 주지는 않는다).

(volleyball도 `volleyball-android` / `volleyball-android-play` 둘이다).

| EAS `development` APK | `com.son0925.jogak` | `5E:8F:16:06:2E:A3:CD:2C:4A:0D:54:78:76:BA:A6:F3:8C:AB:F6:25` | `jogak-android-eas` ✅ |

✅ **위 3줄은 2026-08-14에 Cloud Console 실측으로 대조했다** — 클라이언트마다 상세 화면을 열어
패키지명과 SHA-1을 눈으로 확인했고 **셋 다 이 표와 정확히 일치**한다. `jogak-web`의 클라이언트 ID
(`281316002652-v395…`)도 `eas.json`의 `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`와 같다.
같은 조회에서 **stg 클라이언트가 없다는 것도 확인**했다(프로젝트에 클라이언트 8개, stg 없음).

⚠ **Cloud Console의 클라이언트 *생성* 폼은 자동화가 안 된다**(2026-08-14). `애플리케이션 유형`
드롭다운이 **뷰포트 y≈14~25**에 렌더돼 콘솔 헤더 뒤로 깔리고, `aria-expanded`가 `false`에서
안 열린다 — ref 클릭·좌표 클릭·JS `.click()`·합성 마우스 이벤트·창 리사이즈 전부 실패했다.
반면 **목록과 상세 화면은 멀쩡히 읽힌다.** 생성은 사람이 한다.

⚠ **stg는 패키지명이 달라 클라이언트를 새로 만들어야 한다.** 지문만 추가하는 게 아니다 —
클라이언트는 `패키지 + SHA-1` **쌍**이라 패키지가 바뀌면 무조건 새 클라이언트다.
`webClientId`는 패키지에 안 묶이므로 **그대로 쓴다**(`eas.json`의 stg 프로파일에 같은 값).

Play 앱 서명 SHA-1은 **Play Console → 테스트 및 출시 → 설정 → 앱 무결성 → 앱 서명**
→ **기존 키**의 *SHA-1 인증서 지문*(클릭하면 클립보드로 복사된다). 화면에 글자로 렌더링되지 않는다.
⚠ `양자 내성 암호화 키` 쪽이 아니라 **기존 키**다 — 나란히 있어서 잘못 집기 쉽다.

#### 🔴 앱 서명 키는 **첫 업로드 전에 이미 있다** (2026-08-14 실측)

*"SHA-1을 알려면 AAB를 먼저 올려야 한다"* 고 생각했는데 **틀렸다.** `조각 stg`를 만들자마자
앱 서명 키가 생성돼 있었다 — 지문도 바로 나온다. 첫 업로드를 기다리는 것은 **업로드 키
인증서**뿐이고, 구글 로그인에 필요한 것은 **앱 서명 키**다.

→ **닭-달걀이 없다.** 앱을 만든 직후에 OAuth 클라이언트를 발급하면 **첫 빌드부터 로그인이 된다.**

⏭ **미해결**: 같은 페이지의 디지털 애셋 링크 스니펫이 보여주는 SHA-256
(`09:45:F8:…:CE:66`)이 복사 버튼으로 얻은 SHA-256 어느 것과도 일치하지 않는다.
로그인이 실패하면 **여기부터 의심한다.**

✅ **2026-08-10 로그인 성공.** `jogak-android-eas`를 추가하자 에뮬레이터에서 전 경로가 통과했다 —
구글 계정 선택 → `idToken` → `/auth/login` → 세션 토큰 → 문의 폼. **서버·audience는 처음부터 정상이었고
원인은 SHA-1 하나였다.**

⚠ **실제로 겪음(2026-08-09).** 에뮬레이터에 EAS `development` APK를 깔고 로그인했더니 실패했다.
`unauthorized`가 아니라 포괄 오류였는데 — 구글이 `DEVELOPER_ERROR`로 **서버에 닿기도 전에** 끊은 것이다.
로컬 debug 키만 등록돼 있었고 EAS의 debug 키(`5E:8F:…`)는 등록돼 있지 않았다.

**판별법**: `unauthorized`면 서버/audience, 그 외 오류면 **지문/패키지**를 먼저 본다.
설치된 APK의 실제 지문은 이렇게 확인한다 — 어느 키로 서명됐는지 짐작하지 않는다:

```
adb shell pm path <package>          # base.apk 경로
adb pull <경로> installed.apk
apksigner verify --print-certs installed.apk
```

⚠ **탈퇴(계정 삭제)는 Google Play 정책상 필수다.** 계정을 만드는 앱은 앱 안에 삭제 경로가 있어야 한다.
✅ 문의 화면 하단 계정 줄에 넣었다(2026-08-09) — 계정을 쓰는 자리가 여기뿐이라 여기에 둔다.
⏭ **웹 삭제 URL은 아직 없다.** 스토어 등록 정보에 적어야 하므로 게시 전에 만든다
(처리방침과 같은 GitHub Pages에 페이지를 하나 더 두면 된다).

## 5.5 문의 내역과 답변 (`GET /api/v1/tickets/mine`, 2026-08-13)

**이게 로그인의 존재 이유다.** 익명 문의는 답변을 돌려줄 경로가 없어서 단방향이지만,
주체가 있으면 답변이 돌아온다 — 그런데 **돌아온 답변을 볼 화면이 없었다.**

문의 화면(`app/support.tsx:68`)은 *"답변을 드리려면 누가 보냈는지 알아야 한다"* 며 로그인을
요구해 놓고, 보낸 뒤에는 아무것도 보여주지 않았다. 서버 라우트와 SDK(`fetchMyInquiries`)는
**둘 다 이미 있었고 앱만 부르지 않았다.**

### 화면을 나눈다 — 쓰는 자리와 읽는 자리

| | |
|---|---|
| `app/support.tsx` | **쓰는 자리.** 카테고리·본문·보내기 |
| `app/inquiries.tsx` | **읽는 자리.** 내역·상태·답변 |

한 화면에 합치면 문의를 쓰러 온 사람이 옛 내역을 스크롤해 지나야 하고, 답변을 보러 온
사람이 입력창을 먼저 만난다. 입구는 **두 곳**이다 — 문의 화면 헤더(로그인 상태에서만)와
설정 › 문의 내역.

### 🔴 답변이 왔다는 것을 어떻게 아나 — 배지가 없으면 화면이 있어도 안 열린다

`BACKUP_SYSTEM.md` §5에서 배운 것과 같은 함정이다: **통지 채널이 없다.** 푸시가 없으니
사용자가 스스로 열어보지 않으면 답변은 영원히 안 읽힌다. 화면만 만들고 끝내면
"만들었지만 닿지 않는" 것이 된다.

→ **설정 행에 점을 찍는다.** 공지와 **똑같은 규약**을 쓴다(§4) — 숫자가 아니라 점,
  읽음은 기기에만, 서버에 보내지 않는다.

### 미읽음 키는 `id`가 아니라 **`id:repliedAt`**

공지는 id 집합으로 충분하지만 답변은 **고쳐 쓸 수 있다.** id만 기억하면 운영자가 답변을
정정해도 사용자에게는 이미 읽은 것으로 남아 **정정이 영영 안 보인다.**

```
읽음 키 = `${ticket.id}:${ticket.repliedAt}`
```

`repliedAt`이 바뀌면 자동으로 새 키가 되어 다시 점이 뜬다. 별도 비교 로직이 없다.

### ⚠ 로그아웃·탈퇴하면 **반드시 비운다**

안 비우면 다음 사람이 로그인했을 때 **앞사람의 답변 배지가 남는다.** 내용이 새는 것은
아니지만(목록은 서버가 subject로 거른다) 있지도 않은 답변을 알리는 것은 고장이다.
탈퇴는 더 분명하다 — 서버에서 문의가 사라지는데 로컬에 읽음 기록만 남을 이유가 없다.

→ `auth-gate.ts`의 로그아웃·탈퇴 경로에서 `clearInquiries()`를 부른다.

### 조회 시점 — bootstrap에 실을 수 없다

공지는 `bootstrap` 한 번에 실려 오지만 **문의는 인증이 필요해서 못 싣는다.** 그렇다고
앱 실행마다 부르면 로그인 안 한 사람에게까지 왕복이 생긴다.

| 언제 | 무엇 |
|---|---|
| 설정 탭 진입 | **로그인 상태일 때만** 1회. 문의로 가는 유일한 길이라 여기서 재면 충분하다 |
| 문의 내역 화면 진입 | 항상 다시 읽는다. 답변을 보러 온 사람에게 낡은 목록을 보이지 않는다 |
| 문의를 보낸 직후 | 갱신한다 — 방금 보낸 것이 목록에 없으면 안 간 것처럼 보인다 |

**실패는 조용히.** §3과 같다 — 목록이 안 열려도 일기는 그대로 써진다.

### 🔴 기기에서만 드러난 것 2개 (2026-08-13)

코드만 보고는 둘 다 안 잡혔다. 화면을 띄우고 **네트워크를 꺼가며** 본 값이 이것이다.

| 잡은 것 | 어땠나 |
|---|---|
| 🔴 **세션이 죽었는데 "문의가 없어요"** | dev 토큰이 실서버에서 401 → SDK가 세션을 폐기 → 화면은 빈 목록을 그렸다. **있는지 없는지 우리도 모르는데** 없다고 말한 것이다. `not-signed-in`과 `unauthorized`를 오류 표시에서 갈랐다 — 전자는 화면에 오지도 못하고, 후자는 **지금 그 화면을 보고 있다** |
| 🔴 **오프라인이면 '내 문의' 행이 영영 안 뜬다** | `signedIn`을 조회 성공에서만 켰더니, 초기값 false에서 벗어날 길이 없었다. 로그인한 사람이 비행기 모드로 앱을 열면 입구가 사라진다 → **토큰 유무(`isSignedIn()`, 로컬 읽기)로 판정.** 설정 탭에 왕복을 더하지 않는다는 원칙과 어긋나지 않는다 |

⚠ 둘 다 **"실패를 한 덩어리로 다뤘다"가 원인**이다. `FailReason`은 종류마다 사용자가 할 수 있는
일이 다르다 — 세션 만료는 재로그인, 오프라인은 재시도, 미로그인은 아무것도 아니다.
`unauthorized`에 재시도 버튼을 주지 않는 것도 같은 이유다(눌러봐야 또 401이다).

### 상태 배지와 답변은 **각각 독립적으로 그린다**

서버 `status`는 `open` · `replied` · `resolved` 셋이고, `reply`는 별개 필드다.
**`resolved`인데 `reply`가 `null`인 조합이 가능하다**(운영자가 답변 없이 닫은 경우) —
상태에서 답변 유무를 추론하면 그 칸에서 깨진다.

→ 배지는 `status`만 보고, 답변 영역은 `reply !== null`일 때만 그린다. 서로 묻지 않는다.

⚠ 서버가 **50개에서 자른다**(`LIMIT`). 페이지네이션을 만들지 않는다 — 개인이 50건을
  넘기는 것은 이상 상황이고, 그때 필요한 것은 목록이 아니라 우리가 연락하는 것이다.

## 개발용 임의 로그인 (2026-08-11 결정)

에뮬레이터에서 **구글 로그인 없이** 로그인 상태를 만든다. 실제 로그인은 AAB를 올려
확인하고(사용자), 개발 중에는 그 뒤에 있는 화면들(백업·구독·문의)을 눌러볼 수 있어야 한다.

| | |
|---|---|
| 게이트 | **`__DEV__` + `EXPO_PUBLIC_DEV_LOGIN=1`** 둘 다 |
| 하는 일 | SecureStore의 세션 키에 개발용 토큰을 넣고, 고정된 subject를 세운다 |
| 권한 | 엔타이틀먼트 캐시에 `pro`를 켠다 — 안 켜면 구독 게이트에 막혀 백업 화면을 못 본다 |

### 왜 `__DEV__`를 쓰나 — env 플래그 하나로는 부족하다

`EXPO_PUBLIC_*`는 **릴리스 번들에도 인라인된다.** 플래그만 쓰면 실수로 한 줄이 남는 순간
릴리스 앱에 가짜 로그인이 실린다. `__DEV__`는 릴리스에서 `false`로 접혀 **코드째 사라진다**
— 남아 있어도 실행될 수 없다. 그래서 `__DEV__`가 1차 게이트이고, env는 "개발 중에도
기본은 꺼짐"을 위한 2차다.

### 왜 세션이 안 지워지나

앱의 `EXPO_PUBLIC_SERVER_URL`이 비어 있으면 SDK 호출이 전부 `not-configured`로 떨어져
`restoreSession()`이 **토큰을 폐기하지 않는다**(폐기는 서버가 401로 거절했을 때만).
개발 환경이 정확히 그 상태라 가짜 세션이 재시작을 견딘다.

⚠ **common_server URL을 개발 `.env`에 넣으면 이 전제가 깨진다.** 진짜 서버가 가짜 토큰을
  401로 거절해 로그인이 즉시 풀린다. 그때는 실제 구글 로그인을 쓰는 것이 맞다.

### 서버 쪽 짝

조각 서버의 `AUTH_STUB=1`이 아무 Bearer나 받아 `pro: true`를 준다. **로컬 전용이다** —
`NODE_ENV !== 'production'` 가드가 하나 더 있어 Vercel에서는 켜도 동작하지 않는다(실측 확인).

```
에뮬레이터(가짜 로그인) → 로컬 Next(AUTH_STUB) → 클라우드 Supabase(jogak-stg)
```

⚠ 배포된 stg(`jogak-stg.vercel.app`)는 **가짜 토큰을 401로 거절한다.** 그쪽을 향한
  전체 왕복은 진짜 구글 로그인이 있어야 하고, 그게 AAB 테스트의 몫이다.
